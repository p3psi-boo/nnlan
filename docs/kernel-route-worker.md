# TUN 主机路由：有界后台写入

## 证据与范围

地址索引构建 `48a1…` 修正固定发包数后，千节点初始成员/内核地址核验在 114.464 s
内通过；随后仍有 21/1000 组交换失败（19 次 ping 检查、7 次精确 trace 检查，二者有重叠）。
`target/tun-scale-1000-fixed-count.json` 保留失败结果及完整资源回收记录。
该轮夹具快照为 `target/tun-scale-fixed-count-baseline.py`；后续夹具另外增加后台路由就绪检查。

对该轮 32 个自有 daemon 做 20 s、49 Hz CPU 采样，得到 594 个样本。
`Engine::tick → refresh → Tunnel::sync_routes → HostRoutes::change → sendto → rtnetlink`
调用栈中，IPv4 增删路由进入内核互斥锁等待/自旋；`osq_lock` 自身占这组样本 24.07%。
原始证据为 `target/fixed-count-perf.*`、`target/fixed-count-perf-stacks.txt` 与
`target/fixed-count-perf-provenance.json`。这是单宿主机、选定节点、特定阶段的样本比例，
不是所有节点的 CPU 占比或总加速比；采样干扰未排除。

持久 netlink socket 已消除了逐路由 fork，但 `sendto` 本身仍可能同步进入内核路由处理。
因此，仅把 socket 设成非阻塞或改用异步读 ACK，不足以保证主事件循环不会卡在内核操作中。
本轮只隔离已测得的阻塞路径，不改路由算法、协议版本、地址池或 FEC/RTX。

## 一个写入者，一份最新目标

- 每个启用 TUN 的实例只有一个路由工作线程，持有该 TUN 的 rtnetlink socket 和已确认路由集合。
  无 TUN 实例不创建它。socket 在所属 network namespace 中打开。
- Engine 提交最新的目标地址集合，不排队保存一串历史任务。目标最多为现有节点上限的两倍。
- 同一目标不产生新代次。更新只替换一份 `Arc` 快照；工作线程执行过程中最多额外持有一份旧快照。
- 每次实际内核操作之前检查目标代次；被更新的旧任务停止继续提交，立即重新计算差异。
  正在等待的单次内核操作不假装可取消：收到 ACK 后先记账，再由最新目标补偿。
- 每个快照先删后增。保留 exclusive add、不覆盖既有路由、删除限定接口、收到正确内核 ACK
  后才记为已安装/删除的规则。仍是已知可信节点的 `/32`、`/128`，不是整池汇总路由。
- 内核错误、工作线程退出或状态异常都会使 daemon 明确失败，不把失败变成已就绪。
  原 socket 的发送/接收超时和 ACK 来源、序号、报文检查保持不变。
- 停机先通知并 join 写入线程，再关闭 TUN，避免接口销毁之后后台仍在写路由。

现有 IPv4 本机地址更换、Subnet/Exit 策略与 nft 操作不在此工作线程范围内。
这是专用路由写入者，不是通用任务执行框架。

## 就绪与权限

`status.kernel_routes_ready` 表示最新目标代次的所有主机路由已经得到内核确认。
成员发现与内核就绪分开表达；无 TUN 时该项为 true。千节点夹具要求该项为 true，
再进行原有内核地址与逐包测试，避免只看到成员数量就过早宣布收敛。

成员封禁/撤回仍先在 Engine 中执行，清理会话、待发内容与身份资格。暂未删掉的旧 TUN
路由不赋予身份资格，转发和接收仍各自检查当前信任。原有 VIP nft 防直出规则继续保护
主机路由暂缺的窗口；后台任务不改默认路由、用户接受的子网或 Exit 选择。

`members deny/allow` 的成功响应等待最新主机路由代次完成，但等待不会阻塞 Engine。
每实例最多保留 16 个此类响应，取消的客户端在 tick 清理；超限请求在修改配置之前报错。
内核失败不会发送成功响应。原有持久化失败不改变运行策略的规则保持不变。

## 回归

- 模拟阻塞内核操作时，拥有者仍能查询状态、连续替换 98 个目标。
  只执行在途旧操作、它的补偿以及最新目标，没有历史队列；旧 ACK 不把新代次标为完成。
- 同一目标不重复写入、删除先于新增、空目标完整删除。
- 模拟内核冲突必须成为错误，不得报告成功或继续接受目标。
- 停机等待在途写入结束，不再执行第二次操作。
- `make e2e-tun-routes` 还检查后台线程的 2000 条真实双栈路由增删，只有 ACK 完成后就绪。

规模结果必须引用对应二进制的独立报告，不能沿用 `48a1` 的成功或失败作为新构建结论。

## 启动阶段的第二个阻塞点

`2871…` 后台路由构建的百节点五阶段通过；千节点首轮却在初始 7.36 s 状态观测时
发现 daemon 已退出，尚未进入流量阶段。6 份节点日志明确报告启动时自动网卡快照超过
2 s：`target/tun-scale-1000-route-worker.json`。全部自有资源已回收；这轮不是千节点通过。

启动路径原先先查询一次接口，随后启动的监控又立即“订阅通知→查询接口”，重复查询
不仅多一次子进程，也把非关键发现信息变成了启动失败条件。修正为先用已验证配置中的
候选/peer 启动，动态接口候选完全由已有监控负责；仍立即查询、仍保持单次 2 s 超时、
输出大小上限、事件合并与周期重试。未加无限等待、未提高超时或绕过身份验证。

接口 E2E 夹具增加冷启动快照持续阻塞的情况，要求配置 peer 在 1.5 s 内建立成员关系，
阻塞期间仍完成加密回显；超时子进程必须回收，后续事件触发查询后无需重启即可恢复
自动候选。既有地址变更、快照失败/超时、候选过期与周期恢复检查继续保留。
