# 路由架构调研：先消除平方级工作，再决定是否放弃全网状态

日期：2026-09-22。性质：研究建议，**不是已批准的协议变更，也不是新一轮千节点通过报告**。
后续决定：用户已认可千级规模目标与“先索引、再同步”的执行路线，见 `project-decisions.md`。
下文实验和生产未修改的说明记录调研当时状态；后续实现与验收另记于 `implementation-status.md`。
本轮只增加本文和 `target/routing-research/` 的局部诊断；生产 Rust、配置、线协议没有修改。
现有 release 仍为 `fec5c441c04c77e1560663e7255eacf668dedc4487feeec3adf296be733aec12`。

## 结论与置信度

**针对百节点日常使用、千节点验收、低时延和维护成本优先的当前产品，推荐保留精简的全网
链路状态，把控制面做成有界、可补齐的增量状态同步，并用索引服务数据面。暂不引入 DHT，
也不直接替换成树路由。** 如果未来要让很大的网络中每台设备都只保留局部知识，
Yggdrasil/Ironwood 风格的紧凑路由是值得单独验证的方向，而不是当前测试失败的默认补丁。

对“先修索引、区分同步与收包、保留功能边界”的判断置信度高；对“足以解决真实千节点收敛”
的判断仍需端到端实验。以下区分文献结论、源码事实、局部测量和设计建议。

继承约束中，Rust、单一程序、默认 relay、有界直连、固定地址池、碰撞处理、传递信任、手动
选择子网/出口是实际产品约束；现有 `Record` 字段必须共用生命周期、逐包扫描全记录、
当前 gossip 出队语义则是实现选择，不是必须保留的用户承诺。

## 1. 新的本地证据：问题不等于“存了 999 个节点”

源码路径：

- `src/runtime/mod.rs` 的 `Engine::refresh` 遍历可信记录生成双栈主机路由；对每个远端调用 `ipv4_owner`。
- `src/runtime/control.rs` 的 `ipv4_owner` 每次扫描记录，并在扫描中重新派生地址。
- 两者组合，单次完整路由列表计算接近平方级地址派生；`node_for_ip` 同样通过扫描查地址。
- 收发、管理请求和这段同步计算由同一个 Engine 驱动。因此长计算具备阻塞其他工作的条件。
  这不是“每次续签必然重建”：已有 `dirty` 判断，描述未变的纯续签会跳过重建。

诊断程序直接包含生产 `Control` 源码，并链接现有 release 库；对照方案一次生成可信地址表，
按公钥排序建立 IPv4 归属索引，再生成同样的路由集合。每种规模先断言两个集合一致，
再交替测量 7 次，表中为中位数：

| 节点数 | 现有路由列表计算 | 本次重建索引再计算 |
|---:|---:|---:|
| 100 | 2.93 ms | 0.104 ms |
| 250 | 19.03 ms | 0.286 ms |
| 500 | 79.67 ms | 0.607 ms |
| 1000 | 336.38 ms | 1.279 ms |

对照也计入建立索引的时间，不是只测查表。单进程、无内核路由调用、无网络、无验签/身份生成
和信任收敛耗时；不是生产修复，也不是整体吞吐提升倍数。它明确显示一个实现级热点，
但尚未证明它是千节点失败的唯一根因。原始代码、逐次结果、编译产物映射和哈希：
`target/routing-research/route-scan.rs`、`run-diagnostic.py`、`route-scan.jsonl`、`provenance.json`。

现有周期为 15 s 重签、60 s 有效。在 1000 节点稳态中，若每份新记录都送达其余成员，
仅不重复的远端记录交付就约 `1000 × 999 / 15 = 66600` 次/秒（全网合计；每节点约 66.6 次）。
这只是由当前配置计算出的工作量，不是实际 PPS；重传、重复路径、字节大小和排队另算。
存储是 O(N)，持续刷新与全网复制是另一项成本，两者应分开测量。

## 2. 文献与成熟方案比较

### 2.1 可靠增量链路状态：当前首选的工程方向

OSPF 的链路状态数据库仍描述区域拓扑，但通过摘要交换、请求、确认和重传协调状态，
不是把某次发送当成对端已拥有该版本。这里借鉴的是同步机制，不是引入完整 OSPF、区域配置
或一个独立路由 daemon。[RFC 2328，§10、§13](https://www.rfc-editor.org/rfc/rfc2328.html#section-13)

当前 `Gossip::pop` 在取出身份后移除待发项；`Engine::tick` 只在 `transport.send` 立即返回错误时
重新排队。有限 FEC/RTX 和有期限队列不等于状态可靠送达。因此应核对“对端已应用哪个版本”，
让仍有效的最新状态能通过重试或对账补齐。旧版本被新版本取代，不需要无限重传所有历史消息。

Plumtree 将部分链接用于推送完整消息，其余链接用于消息标识通告，缺失时请求正文，并能修复
广播树。它减少的是冗余正文传播，不会让要求全网复制的状态神奇地只占局部空间；本文建议先
借鉴摘要/按需补齐思想，不把完整广播树协议叠加进当前实现。
[Leitão 等，Epidemic Broadcast Trees，SRDS 2007](https://asc.di.fct.unl.pt/~jleitao/pdf/srds07-leitao.pdf)

Trickle 提供一致时降低发送频率、发现不一致时更快同步的调度思路。但它的广播监听与抑制假设
和本项目加密点对点链路不同：B 的确认不代表 C 已有同一状态。只借鉴退避/去同步原则，不直接
照搬抑制计数，更不把 Trickle 当成可靠存储协议。
[RFC 6206](https://www.rfc-editor.org/rfc/rfc6206.html)

### 2.2 Babel：真正的替代路由，但不是“只存邻居”

Babel 使用距离向量和带序号的可行性条件避免路由环路；节点可以只了解目的的下一跳/距离，
而非全网边集。若平坦地址的每个节点都要可达，仍需按目的维护路由，并不意味着每节点只存几条。
它还包含周期更新，RFC 明确指出大型稳定网络下这会比可靠增量协议产生更多控制流量。
[RFC 8966，§1.2、§2、§3](https://www.rfc-editor.org/rfc/rfc8966.html)

对本项目的判断：若测量证明全网拓扑维护、动态选路是主要负担，Babel 是应认真比较的候选。
但它不直接提供我们的传递引荐、地址声明冲突、同 CIDR 多发布者选择语义；这些仍需保留并正确
绑定身份。另用 `babeld` 增加服务和集成面，自行“仿 Babel”则承担可行性、序号请求、撤回等
正确性维护。此阶段不把换 Babel 当作免除记录同步成本的方法。

### 2.3 Yggdrasil / Ironwood：局部知识可以工作，但付出查找与路径代价

必须区分版本。Yggdrasil 2023 年 v0.5 设计文章描述以 Bloom filter 引导的树上查找替代此前
DHT 路由，并恢复贪心路由；不是把 v0.4 的 DHT + source routing 介绍当成现在的设计。
文中也明确指出：固定大小过滤器可能在网络核心饱和，增加查找流量。
[官方 v0.5 设计说明](https://yggdrasil-network.github.io/2023/10/22/upcoming-v05-release.html)

Ironwood 当前 README 描述：节点交换相关树祖先信息，查找公钥对应的树位置，再在树度量空间
贪心转发；路径断裂时通知源重新查找。“每邻居常数状态”描述的是 Bloom 查找状态，不应扩大成
整个协议状态在任意拓扑中均为 O(1)；还存在祖先信息、坐标、会话和缓存等状态。
[Ironwood 官方实现说明](https://github.com/Arceliar/ironwood#routing)

对本项目的判断：这是未来更大规模、稀疏通信的强候选；代价包括首次查找、错误坐标恢复、树
变化、过滤器误判、路径 stretch，以及热点节点负载。自动树根不是需要用户配置的中心服务器，
也不意味着每个数据包都必经根；但零配置不代表没有结构性热点。需实测，而不是凭架构名称
承诺低延迟。照搬其 Go 库也不是保持现有 Rust/FEC/UDP 栈的零成本操作。

### 2.4 紧凑路由论文：有理论收益，但论文没有替我们解决身份定位

Thorup–Zwick 在一般加权无向图模型中给出路由表大小与路径 stretch 的权衡，例如
近似平方根状态、stretch 3 的方案。论文同时明确将“源如何取得目的标签”放在研究范围之外。
这些是特定标签/预处理模型下的结论，不是动态加密覆盖网现成协议，更不是 Yggdrasil 的性能保证。
[Compact Routing Schemes，SPAA 2001，原论文](https://graal.ens-lyon.fr/~abenoit/reso05/papier/thorup-tree.pdf)

本项目的稳定地址来自公钥哈希，拓扑会变；即使转发状态变小，也还要解决
`IPv4/IPv6 → 身份 → 当前位置`、成员资格、碰撞和失效恢复。选择紧凑路由，是用路径/查询/维护
代价换状态，而不是删除成本。

### 2.5 SWIM、HyParView、Kademlia、AODV 各解决什么

- **SWIM**：把故障检测与成员更新传播拆开，但应用仍可拥有全成员表；不提供本项目的多跳转发。
  随机目标探测也不是 NAT 限制下任意节点均可直达的证明。
  [Das 等，SWIM，2002](https://www.cs.cornell.edu/projects/Quicksilver/public_pdfs/SWIM.pdf)
- **HyParView**：维护小的活跃视图和较大的备用视图，提升 gossip 覆盖网络恢复能力；不是目的路由表。
  本项目已有有限邻接和按需连接，值得借鉴备用候选管理，不值得为“减少全网状态”另加整套协议。
  [Leitão 等，HyParView，DSN 2007](https://joaoleitao.org/pdf/HyParView.pdf)
- **Kademlia**：提供基于 XOR 的键值/节点查找，原协议返回 IP/UDP 端点供 RPC 使用。
  查到地址并不等于找到了可走的中继路径；在节点任意互访受限时，单独加 DHT 没有解决路由。
  [Maymounkov、Mazières，2002](https://pdos.csail.mit.edu/~petar/papers/maymounkov-kademlia.pdf)
- **AODV**：按需发现多跳路由，适合减少无业务目的的路由维护；首次业务需要发现过程。
  扩展环搜索也可能走到全网发现；大量并发新目的会把开销集中到请求阶段。
  [RFC 3561，§6](https://www.rfc-editor.org/rfc/rfc3561.html)

## 3. 不因换路由而消失的需求

### IPv4 自动分配与碰撞

`33/8` 只有 24 位主机空间。若初始哈希均匀独立，1000 个节点至少发生一次碰撞的概率约 2.93%，
10000 个约 94.92%；这是生日问题的计算，不是测得的故障率。分区允许各自使用重复地址，
重连后再确定性解决，符合现有实现；两个失联分区各自分配同一候选地址时，冲突信息只能在恢复通信后被协调。

采用局部知识路由后，也仍需让冲突的两份已认证声明相遇。广播声明、分布式目录、树聚合等都
有费用，不应宣称用了 DHT 就自动获得无冲突分配。当前全网精简声明加归属索引是最直接的方案。

### 传递信任与撤销

当前规则不是“曾经有一条证书链就永远可信”：它从真实直连出发，沿未过期签名引荐计算资格。
描述过期或最后一条引荐消失会清理密钥、队列和 VIP 路由。若采用局部缓存/更长寿命身份记录，
必须重新说明缓存证据有效期、引荐撤销传播、断开后信任循环和本地 deny 的优先级。

因此建议先在现有 60 s 有效期与 15 s 续签约束下优化同步与索引。后续若解耦身份、声明、
邻接三个生命周期，须先写出等价或经用户认可的新撤销语义；不是直接取消 TTL 或延长 TTL。
缓存身份材料与当前可通信资格是两件事。

### Subnet、Exit 与多跳 trace

- 子网声明键仍为 `(发布者身份, CIDR)`；相同 CIDR 的不同发布者不应被路由算法悄悄合并。
- 接受哪个发布者由用户决定；RTT 更小不等于授权替换 Subnet Router 或 Exit Node。
- 出口或已选子网失联时继续 fail-closed，不因路径算法变化回落明文网络。
- trace 返回实际经过的中继，不是单纯显示预测路径；所有候选架构都要保留这项测试。
- 去掉全成员副本时，`members`/发现列表要明确是缓存视图还是全网查询结果，不应将局部列表称为完整网络。

## 4. 推荐目标：保留一份精简全网事实，让热路径只做查表

这里的“更好”定义为功能完整、低时延、控制面有预算、维护面小，而非仅追求最小路由表。
零遗留代码的思考实验也得到同样结论：在当前规模，先保留可解释的链路状态模型，而不是同时
建设一个成员协议、DHT、树路由与源路由混合体。

建议结构（设计方向，未接入生产）：

1. **有界签名事实表**：仍保留需要全网传播的精简状态，已有序号、过期和引荐规则先不变。
2. **地址与下一跳索引**：一个可信状态快照生成 IPv4 owner、IPv6 owner、必要的下一跳；
   碰撞以完整公钥排序决胜，撤销/过期/重启原子失效。不应让索引绕过成员资格检查。
3. **逐邻居版本同步**：发送队列不保存多个过时正文；同一身份只保留最新有效目标版本。
   接收确认针对已验证并安装的状态，不是“UDP 收到了”。摘要用于找差异，不代替原作者签名。
4. **有界补齐与背压**：限制每轮处理量、未确认窗口、对账分页和重试成本；避免一个 peer 拖住所有节点。
   较新版本覆盖较旧版本；失效邻接、已过期版本和撤销有明确终止条件。
   保留共享带宽/FEC/RTX预算，不引入一条无限重传、无拥塞约束的旁路。
5. **生命周期拆分作为第二步**：仅在撤销语义与重放测试明确后，把低频身份/地址/服务声明和
   快速邻接变化分开。更新一个端点不应无条件重做所有与它无关的工作。

### 要删除 / 合并 / 拆开

- 删除按目的反复派生全网地址的扫描；合并到一个受成员状态约束的地址索引。
- 删除“成功入发送队列就等于状态同步完成”的假设；确认、补齐和最新版本去重归一个同步模块。
- 拆开“知道身份”“身份当前可信”“当前有可用路径”“用户接受其子网/出口”这四种判断。
- 不引入 DHT、超级节点、完整 OSPF/Babel daemon 或第二条可靠 IP 数据流来绕过问题。
- 保留 Noise、逐跳 FEC/RTX、TUN、配置 UX、trace 和路由选择语义；不是重做所有网络层。

### 三条路径

| 路径 | 内容 | 代价与结论 |
|---|---|---|
| Conservative path | 只修索引与重复工作 | 最快测出实现成本；作为第一个实验，不是完整控制面设计 |
| Clean target | 精简链路状态 + 有界版本同步 + 索引热路径 | 当前推荐的目标；仍是 O(N) 记录，换取简单的定位、碰撞与权限解释 |
| Staged clean path | 先索引对照，再逐项替换同步，最后评估生命周期拆分 | 推荐执行方式；每步独立回归，不长期保留双套路由/同步开关 |

## 5. 证据路径与推翻条件

首个证明点已经完成的是局部对照，不是生产验收。下一步先把索引做成生产等价改动，补齐
碰撞/撤销/过期/重启回归，再按原门槛重跑千节点。与此同时记录实际事件循环停顿与 CPU 栈。
如实际热点不是这部分，则承认微基准解释力有限，继续基于运行证据定位。

之后比较：原版、索引版、可靠增量同步版；不同时改路由算法、TTL、验签限额和底层拓扑。
测量 CPU/RSS、控制流量字节数、重复验签、状态滞后、P95/P99 收发延迟、首次连接时间、
吞吐/PPS、路径相对最短路径的代价、分区恢复和撤销生效时间。

拓扑除了现有三叉树，还要有带环随机图、带捷径图、地理高 RTT/低带宽边，以及热点 Subnet/Exit。
单一树上只有一条路径，缺少比较不同算法选路质量的条件。区分“千 daemon 共用宿主机”的调度压力
和跨机器网络结果。建议多 seed 与持续负载；具体性能验收阈值另行冻结，本文不虚构已通过数字。

**推翻当前推荐的条件**：去掉实现级热点、补齐同步后，全网状态的实际维护费用仍超出目标设备
预算；或业务明确要求万级以上、每节点仅少量通信且内存/空闲流量严格受限。此时制作紧凑路由对照原型，评价完整身份定位/碰撞/撤销成本，而非只比
树转发表大小。若树方案明显增加 P99 延迟、恢复时间或中继热点，则不因内存变小就判它获胜。

若验证真正的局部知识架构，应改用测试端的全局 oracle 核对通信与权限，而不是继续要求产品
每个节点列出全部成员；这属于架构验收定义调整，需要明确记录，不应悄悄降低原测试门槛。

## 6. 收益账单

| 动作 | 付出的成本 | 去掉的具体问题 | 最早能验证的时点 |
|---|---|---|---|
| 可信地址索引 | 一份受控派生缓存和一致性测试 | 路由生成平方级派生、按包扫描身份表 | 已有局部结果；下一轮真实 TUN |
| 逐邻居版本补齐 | 有界窗口、确认、重连对账状态 | 入队后丢失只能等周期再广播，导致版本长时间落后 | 丢包/限速与分区恢复测试 |
| 分离判断与生命周期 | 明确撤销/重放语义，必要时版本升级 | 低频声明与快速邻接互相触发无关更新 | 故障/撤销回归与稳态控制流量 |
| 暂不加入 DHT/树路由 | 接受 O(N) 精简记录 | 避免再造身份定位、IPv4 注册和双路由维护 | 本轮架构选择即省下复杂度；规模边界继续测 |

结论不是“链路状态永远最好”，而是当前发现的平方级工作和同步语义缺口值得先解决；
减少每节点存储并非当前收益最大的第一步。只有完整代价的对照实验，才足以推动下一次路由架构替换。
