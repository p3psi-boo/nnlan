# GGB3：先减少包数和无效填充

后续紧凑包头/ACK 与小包处理改进见 [紧凑数据记录](compact-data.md)；本文保留本阶段结果。

2026-09-22。本轮针对线上开销，不关闭 FEC/RTX，不改密钥/身份，不提高带宽预算。
先做两项不需要新身份映射、能力协商消息或第二条数据通道的改动；源/目标公钥和帧字段暂时保留。

## 已实现

### 1. 认证探测允许更大的数据报

UDP 载荷最大值从 1232 扩展到 1452 字节，后者加 IPv6/UDP 头后为 1500 字节。
这不是把所有路径直接认定为 1500 MTU：仍从 548 开始，只有当前路径/密钥世代、token、尺寸
和时限都匹配的加密确认才能增大实际发送长度。黑洞、ICMP/本地 EMSGSIZE、非对称方向和
换钥沿用原状态机。探测原则参考 [RFC 8899](https://www.rfc-editor.org/info/rfc8899/)，不是宣称实现其全部状态机。

扩大前先确认旧版上限 1232，再尝试 1452。旧节点忽略超大探针时，新节点保留已证实的 1232，
不因二分搜索退到 1226 一类略小尺寸，避免将原来刚好单片的包拆开。
没有更改 GGB3 帧布局；旧解码器支持本轮发送的较短 parity，扩展长度需先取得对方实际确认。
旧节点之间行为不变，新旧混用仍可能因 MSS/分片差异具有不同性能，互通不等于性能完全相同。

- `status.neighbors[].pmtu.maximum_udp_payload` 是本地能力上限，`udp_payload` 才是当前已用大小。
- TCP advertised MSS 取“链路单片可容纳的内层 IP 长度”和“实际 TUN MTU”的较小值，再减去 IP/TCP 基本头。
  默认 TUN 1280 下为 IPv4 1240 / IPv6 1220；TCP 时间戳选项还占 12 字节。
  TUN 1420 时为 1263 / 1243。测试覆盖 1280、1300、1420、9000，避免对小 TUN 广告过大的接收包。
- TUN 默认 MTU 仍为 1280。小路径、旧接收端和多跳仍按实际逐跳 PMTU 做覆盖层分片；不依赖 IP 分片。
- 原有 UDP GSO 仅在确认 1232 或 1452 的档位启用；其他探测所得尺寸保守逐包发送。
- 测量夹具从本地能力上限判断“完整路径已收敛”，旧二进制缺省为 1232；不是将任意观测到的小尺寸都当作通过。

### 2. FEC 只补齐到本组所需宽度

原先无论实际源片多短，都先补零到路径最大 shard 长度，因而很多零也随 parity 发到网络上。
现在原始源片仍立即进入发送队列，封组时才将用于编码的副本补齐到：

```text
max(本组最长源片长度, GGB3 旧解码器接受的最小 shard 长度 489)
```

RS 的 K/M 选择、最多 8 片/2 ms 封组、数据与修复共享预算、RTX、原始包和修复包反馈语义不变。
每个组的 parity 长度一致，携带完整原始分片头和数据；较短源片在接收侧依照原有规则补零。
保护预算仍按实际字节记账；成本降低后某些原本被预算拒绝的修复包可能得到准入，
不能把“策略未改”误说成所有场景实际发送的修复包数都必然一样。

小包组的校验 shard 可从旧满尺寸 1173 降到 489，计入现有线上预算的单片 parity 从
1273 降到 589 字节。这个收益是特定小包组的校验片，不是整张网络吞吐提升 54%。
默认 TUN 满尺寸数据包在新路径的实际 shard 为 1370，只需填到 1370，不必填满 1393。

### 资源边界

没有新增工作线程、队列种类、身份表或用户配置；认证、重放窗口与状态撤销保持。
队列/缓存条数和时间界限未变，但每项允许的最大载荷增加，所以峰值字节容量可能增加。
例如 2048 个最大源片多约 440 KiB 载荷容量；并非不增加任何内存/积压成本。
原先 20 ms RTT 满载排队问题仍需单独测量，不用更大包或“无 TUN drops”代替背压设计。

## 收益预期及下一步

默认 TUN 1280、IPv4 TCP 含时间戳、满 8 片组配 1 个 parity 时，原始应用数据从约 1031
增到 1228 字节；按现有保守 IP/UDP 预算，理想有效比例约从 71.0% 到 73.4%。
这一步只预期几个百分点的满载 TCP 改善，不会自然变成 900 Mbit/s。

1200 字节 UDP 载荷则由原来的两个源片变成一个；同一业务量所需包数、重组及修复开销
可能明显减少。用固定提供负载比较字节和丢失，而不是只比较发送端报告的速率。

更大的格式收益应分下一轮单独做，避免同时改变太多变量：

1. **紧凑单片头**：源序号已能由 FEC 组号和索引得出，单片包没有必要重复携带全部分片字段。
   FEC 恢复后仍需确定实际长度；不能直接把所有长度信息删掉。消息/源片重放序号也要统一定义。
2. **直连数据复用会话身份**：仅当消息起点就是发送邻居、终点就是接收邻居时，双方身份已由
   Noise 会话确定，可以省去逐包两份公钥。中继业务、签名 trace 等保留完整语义；接收后转为同一种
   内部消息，继续共用验证、路由、FEC 和预算，不复制两套网络栈。
3. **多跳身份压缩放后面**：暂不引入全网短 ID 分配/同步协议，也不把公钥截断当作不会碰撞。
   若以后采用短索引，必须处理冲突、未知记录、撤销和重启，并与完整身份绑定。

这些帧布局改动需要明确的新版本或认证能力协商；本轮未实现，不悄悄借“探针更大”暗示其他未协商能力。
FEC 比例/组规模调整也是另一项弱网实验，不在这里偷偷降低保护来提高跑分。

## 实测与验证

### 配对性能

基线 `2a1462496d00b4fd96d7d81ff78652a8e1e64b0931290344123306e73bb141b2`；
本轮 release `80e5d6c6f0e9e23e413e15ef65b1718c154d8b6b78ab43027a148bc2b8c828a4`。
同一台 Xeon Gold 5218 / Linux 6.18.46，64 个逻辑 CPU，不绑核；独立 network namespace，
双向 1000 Mbit/s 整形，默认 TUN 1280、BBR 单 TCP 流、FEC/RTX 开启。
每次预热 20 s、测量 15 s、满载期间 50 次/s ICMP；编译与其他网络测试不与测量重叠。
三轮顺序为旧→新、新→旧、旧→新。不是两台物理机器的网卡线速测量。

| 直连 IPv4 | 原版 goodput Mbit/s | 新版 goodput Mbit/s | 原版 RTT p99 ms | 新版 RTT p99 ms |
| --- | ---: | ---: | ---: | ---: |
| 第 1 轮 | 700.21 | 723.89 | 3.92 | 3.84 |
| 第 2 轮 | 700.42 | 723.73 | 3.89 | 4.51 |
| 第 3 轮 | 700.29 | 723.75 | 4.32 | 3.63 |
| 中位数 | **700.29** | **723.75** | **3.92** | **3.84** |

吞吐提升 **3.35%**。两端进程 CPU 中位数从 74.18%/61.94% 降到 70.39%/58.21%
（100% 表示一个逻辑 CPU）。六次均收到 750/750 ICMP，TCP 重传为 0，TUN 丢包为 0；
两端通用 daemon dropped 每次各增加 1，并非宣称所有丢弃计数都是零。
p99 单轮有升有降，这不是可靠的大幅降延迟结论。
新版单次 IPv6 711.94 Mbit/s、p99 3.95 ms；反向 IPv4 723.73 Mbit/s、p99 4.49 ms。

额外两个路由 underlay 场景各只有一对样本（不是 overlay 多跳性能）：

| Underlay 条件 | 原版→新版 goodput Mbit/s | 原版→新版 p99 ms | 原版→新版 TCP 重传 |
| --- | ---: | ---: | ---: |
| RTT 20 ms，无注入丢包 | 515.79→586.87 | 68.3→66.5 | 0→0 |
| RTT 20 ms，双向各 1% 丢包 | 514.12→576.77 | 63.8→68.9 | 61→53 |

均 750/750 ICMP、TUN drops 0。高 RTT 满载排队仍在；1% 丢包样本的尾延迟反而上升。
无丢包样本 daemon dropped 旧/新均为两端各 1；1% 样本旧为 26/1，新为 1/1。

### 固定业务量的字节成本

`packet_efficiency.py` 使用接收端 iperf UDP 统计，不以发送端速率代替交付速率。
下面“字节比”是 **A 端协议记账发送字节 / B 端接收应用字节**：包括 A 的控制/修复发送，
不包括 B 的反向流量；计数按 IPv6 IP/UDP 48 字节保守记账，即使实际 outer 为 IPv4。
它不是抓包实测的物理线路字节，也不是 UDP 最大吞吐。各组只有单轮配对。

| UDP 应用载荷 / 提供速率 | 原版→新版接收 Mbit/s | 丢包率 | 原版→新版字节比 | 字节成本降低 |
| --- | ---: | ---: | ---: | ---: |
| 1200 B / 100 Mbit/s | 100.00→100.00 | 两者 0% | 1.58181→1.34565 | **14.93%** |
| 300 B / 50 Mbit/s | 50.00→50.00 | 两者 0% | 2.32192→2.03687 | **12.28%** |

1200 B 场景 A 的源片约 312567→156304，parity 39074→19540；
300 B/50 Mbit/s 的源片约 312549→312555，parity 均 39071，后者主要体现较短填充的收益。
以上四次 RTX 为 0，源队列/未发源片/TUN 丢包为 0，通用 daemon dropped 两端各 1。

**负面结果同样保留**：300 B 提供 100 Mbit/s 时，旧/新只接收到 85.32/85.33 Mbit/s，
丢包 14.67%/14.66%，A 的 daemon dropped 增加 91716/91644，TUN drops 仍为 0。
本轮未定位该通用丢弃计数的具体原因，不能断言是 CPU 极限或网络丢包；降低协议字节
没有解决这个小包负载的交付瓶颈。50 Mbit/s 是随后追加的零丢包成本对照，不替换高负载结果。

原始 TCP/UDP、CPU、计数和夹具来源哈希位于 `target/packet-size/paired/`，
TCP 汇总为 `target/packet-size/paired-summary.json`。仅扩展 MTU 的早期试跑为
`mtu-pilot.json`（722.41 Mbit/s），不混入最终三轮中位数。
首个 UDP 1200 B 基线启动后采样工具补充了来源哈希字段（测量逻辑未变）；其原脚本保存为
`packet_efficiency-before-metadata.py`，原报告 `udp-before.json` 保留。
最终表格使用相同冻结夹具的 `udp-before-refresh.json` 与 `udp-after.json`，不是删去负面数据。

```bash
nix develop --command make check
nix develop --command python3 tests/e2e/tun_routes_netns.py
nix develop --command python3 tests/e2e/pmtu_netns.py --output target/pmtu-expanded.json
nix develop --command python3 tests/perf/packet_efficiency.py \
  --binary target/release/nnlan --length 1200 --offered-mbps 100
```

新增普通测试验证两种满源帧分别适配 IPv6 MTU 1280/1500、旧接收端/最小 IPv6 路径在多轮
扩展探测和定期重试后保持 1232、不超过 TUN 的 MSS，以及长短混合组丢失最长/最短源片、
parity 先到/后到、禁 RTX 下 RS 仍完整恢复。

### 回归与可复核材料

- `build-v3.log`：fmt、Clippy `-D warnings`、173 项 Rust 普通测试和 14 项 Python 测试通过；
  真实内核 2000 条双栈路由增删/冲突保护/ACK 测试通过。`final-build.log` 另记录冻结源码后的
  Python 检查、真实内核 plain/offloaded TUN I/O 专项，以及 Nix release 包构建/包内测试通过。
- `regression/`：PMTU、旧版互通、overlay 强制碰撞、多跳成员管理、Subnet Router、Exit Node、
  IPv6 discovery、DHCP policy、TUN offload 九套场景，32 组 weaknet，以及自然 crossed-rekey。
  后者 120 s 持续负载收到 **6000/6000 ICMP**，观测到的最低已证实 PMTU 为 1452。
- `compatibility-final.json`：旧/新两方向 16 KiB echo、trace、双栈 1280 TUN ping、双栈 TCP。
  最后等待 FEC 恢复和发送队列清空，在旧接收端用 nft 精确丢弃 8 个短源包（同长度 RTX 也丢弃），
  实际 drop counter 为 8，旧端 FEC recovery 增加 8，8 次 echo 全成功；不是用 RTX 冒充 FEC。
- 失败记录保留：`build.log` 最初新增帧测试用全零伪 shard 被正常校验拒绝，改为真实 Fragment；
  `compatibility.json` 的随机丢包场景未观察到要求的 FEC 恢复，不能从随机结果证明互通能力，
  原脚本存为 `compatibility-random.py`。随后确定性夹具第一次因 nft 定义间缺换行出现语法错误，
  报告为 `compatibility-deterministic.json`，原脚本为 `compatibility-nft-syntax.py`。
  修复夹具后以更强的确定性恢复断言通过，未删除恢复断言。
- 本轮**没有重跑百/千节点、完整 NAT 矩阵或开机/DHCP VM**；`daemon_scale.py` 只更新了与
  实际能力匹配的 PMTU 就绪条件，旧规模结果不自动当成本轮验收。

构建前后源码、二进制、试跑和正式测量均保存在 `target/packet-size/`，最终哈希清单见
