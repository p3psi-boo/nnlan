# 高 RTT：待确认容量与 TUN 准入背压

本页记录第一阶段；其中暂停 TUN/暂存读批次的实现已被后续 [按流排队](queueing.md) 替代。
待确认缓存与链路准入部分继续保留，下面的旧测量不代表新构建。

2026-09-26。上一轮扫描优化是基线，见 [高 RTT 记录](high-rtt.md)。
本轮把保留副本的空间与未发送工作量分开；不修改线上格式、FEC 开关、重传次数、保护预算或加密层。
这是发送侧资源准入闭环，不是新增 BBR，也不是对所有内核/多跳队列的端到端流控。

## 实现边界

### 待确认缓存

- `Controller::retention_bytes` 按当前发送速率 × `min(1.5 × RTT + 10 ms, 500 ms)` 计算保留空间，最多 32 MiB。
- 按当前路径的完整源片线上大小换算为 2048–16384 项。小包也受项数上限约束，不按 PPS 无限扩容。
- 这是缓存准入上限，不是预分配，也不直接改变 pacer 的允许发送速率或令牌。
- 全部邻居、全部密钥世代共享 **32768 项**源片额度；消息的全部分片一次预留。
  ACK、未发过期、缓存寿命到期、撤销、路径切换和世代删除均通过源片的 RAII 释放额度。
  它是源片的数量/存储边界，不是整个进程 RSS 的上限；FEC、重组、队列还有各自上限。
- 估计速率/RTT 下降导致上限收缩时，不提前删除在途修复副本；停止新准入，等待 ACK 或原有过期释放。
- 单世代动态上限与实例共享硬上限同时生效；没有为每个邻居预留一份最大窗口，也没有新增反馈协议。

### 未发送工作量与本机 TUN

- 原有硬发送队列 2048 项、250 ms 未发寿命、1 s 源片缓存寿命保持。
- 本机 TUN 增加软准入门槛：当前速率对应 5 ms 工作量，限制在 **48000–256000 字节**。
  原有队列加上下一条消息的源片线上字节超过门槛时先不准入；这是字节水位，不是所有速率下的 5 ms 延迟保证。
  封组/修复可能在此后追加，仍服从原来的硬队列、预算和过期规则。
- 用原有 Reader 的最多 128 段缓冲保留未消费的头部，不复制成另一条无界队列。
  暂停的是 `select!` 的 TUN 分支；UDP 接收/ACK、pacer、维护、管理和退出分支继续处理。
- 每次 UDP/定时器/管理事件后重新检查空间。有效 ACK 释放缓存或发送调度消耗队列后，TUN 自动恢复。
- 同一头部连续 **20 ms** 没有准入进展，或整个批次从第一次受阻起已达 **250 ms**，
  到下次调度检查时丢弃剩余批次并记录。真正消费一个包只重置头部停滞计时，不续期批次的绝对寿命。
  这样冷启动 pacer 可以逐步处理一个 64 KiB GSO 突发，而不会因正常处理超过 20 ms 就丢尾段。
  单 TUN 的跨目标队头阻塞仍有界，但这不是每流公平排队。
- 重试时重新解析 IP 来源、当前成员资格、出口/子网策略、当前下一跳和紧凑格式/分片容量；不保存旧路由或密钥引用。
- 中继和覆盖控制消息仍使用原来的硬有界准入；不在 UDP 接收处理中等待下一跳腾出空间，避免阻塞反馈。
  因而本轮没有实现逐跳远端接收信用或保证 IP 可靠交付。

### 明确没有改变的部分

TUN MTU、txqueuelen=500、GSO 上限 65535/128、内核 qdisc、FEC 抑制语义、ACK 节拍、
RTX 次数及保护预算不变。待确认副本不是待发送积压，扩容不直接扩大未发队列。

仅暂停读 TUN 并不保证把背压传到应用 socket，也不保证内核里没有积压。
Linux TUN 的发送路径在放入 `tx_ring` 前会 `skb_orphan`，环满走丢弃路径；
不要把它当成自动等待用户态消费的可靠流控设备。
参考 [Linux v6.18 TUN 实现](https://github.com/torvalds/linux/blob/v6.18/drivers/net/tun.c)。
当前实现应结合交付率、实际排队和满载 RTT 评估，不只看吞吐或成功回复分位数。

## 可观测性

- `status.neighbors[].link.source_cache_limit`：当前世代源片准入上限。
- `transport_cached_sources`：整个实例的当前源片使用量（各邻居显示的是同一个总数）。
- `admission_queue_bytes`：本机 TUN 的软工作量门槛。
- `status.tun_backpressure.pauses`：暂停次数，不是丢包次数。
- `expired_packets`：已读批次等待超时后丢弃的 IP 段数，也计入 daemon `dropped`。
- `max_wait_us`：从该批次第一次暂停开始，到恢复处理/丢弃时观察到的最大时间，包含批次内后续处理。

新字段从进程启动累计；性能测量要比较前后差值，不把预热阶段累计计数算作稳态。

## 验证入口

```bash
nix develop --command make check
nix develop --command make e2e-backpressure
```

新增普通测试覆盖共享额度原子预留与释放、无副作用预检、非法 ACK 不释放、合法 ACK 重新开放准入、
缓存上限扩大/收缩、软水位早于硬包数限额阻止新 TUN 工作量，以及停滞重试不续期、冷启动持续进展不触发停滞超时、部分消费后批次绝对期限不续期。
新三节点真实 TUN 测试覆盖双栈过载、UDP/管理继续响应，以及过载期间成员撤销、另一条路径继续通信。

基线：`f4d823f71660976dc31308f623f0353ffc00839d582633d8e839db8a289143b1`。
最终：`18dec2ed397503df0e8071c4d46dfe6b5e72e93ba33017650ad3dad72cfae137`。

同机 Xeon Gold 5218 / Linux 6.18.46、千兆整形、TUN 1280、内层 BBR 单 TCP 流、
20 s 预热 + 15 s 测量、50 ICMP/s。RTT 场景经过第三个路由 namespace，禁用故障边界的聚合卸载，
验证没有超大 GSO skb 绕过逐包延迟/丢包。正式测试不采样、不与本轮编译或其他网络测试并行。
这是软件 namespace 的测量，不是实际物理网卡/WAN 测试。

每种条件各一轮，不作统计显著性结论。先执行基线与候选 v1 对照，修复 v1 的 GSO 问题后重测最终版；

## 失败候选与修正

候选 v1（`95888143644dd81fd7cafdd38622c9c9d169a6274e9db393dd830fad17a4f712`）
已经改善高 RTT 吞吐，但把整个 GSO 批次的等待统一限制为 20 ms。
在冷启动 8.1 Mbit/s pacer 下，正常 48×1200 B 突发的持续准入超过这个时间；
真实 offload 回归因此丢失 11 个尾段、应用超时。没有放宽测试或加入应用重试来掩盖。

最终版分开“头部无进展 20 ms”和“批次绝对寿命 250 ms”：消费一个包只更新停滞判断，
批次寿命不续期。原来的双栈双向 128×100、48×1200、64×900 B 无应用重传回归连续三轮通过，
随后完整本轮网络回归中的 offload 再次通过。v1 源码、二进制、失败证据与性能数据保留在 `candidate-v1/`。
更早诊断 pilot 的 530.65 Mbit/s / p99 311 ms 位于 `pilot100.json`，不是最终正式测量。

## 完成验证与剩余工作

- fmt、Clippy `-D warnings`、**189 项 Rust**（171 lib + 18 integration）、**16 项 Python**、release 构建通过。
- 新过载背压/成员撤销、PMTU、旧格式互通、IPv4 碰撞/多跳、成员策略、offload 均通过。
- 默认 FEC+RTX 模式的 **8 组双栈弱网**通过；不是完整四模式 32 组矩阵。
- 自然交叉换钥、120 s 连续 TCP+ICMP，**6000/6000 ICMP**，换钥后双栈及反向业务通过。
- 未重跑百/千节点、完整 NAT、独立 Subnet/Exit/DHCP/开机 VM、两个 ignored 内核 Rust 测试或 Nix 包构建。

剩余重点：定位并治理 TUN/内核侧积压，避免把等待简单移到 Reader 看不见的位置；
当前额外延迟没有逐段完全归因。进一步建立多目的/多流隔离与实测服务率约束，再优化满载尾延迟。
这一版没有新增拥塞控制阶段，也没有改变 FEC 抑制策略，不将其标记为整个高 RTT/低延迟目标完成。
