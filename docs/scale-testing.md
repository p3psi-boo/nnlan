# 独立进程与真实 TUN 规模测试

`daemon_scale.py` 验证无 TUN 的控制面与加密数据面；`tun_scale.py` 验证真正的 Linux TUN、
IP 流量、分区合并及重启。两者证据分别记录，不互相代替。

当前 GGB3 使用[单层逐跳加密](hop-encryption.md)。下面按构建记录的历史规模结果
保留当时的协议语义，不视为 GGB3 已经重新通过百/千节点验收。

## 无 TUN 独立进程夹具

```bash
nix develop --command make scale
nix develop --command python3 tests/scale/daemon_scale.py --nodes 1000 --seconds 65 --output target/daemon-scale-1000.json
```

`tests/scale/daemon_scale.py` 启动指定数量的真实 release daemon，不用内存里的节点对象替代进程。
每个进程有独立身份、配置、持久状态、Unix 管理 socket 和实际 UDP 监听端口。
只用本机 loopback，不改宿主机接口、路由、防火墙或 sysctl；退出时只终止并回收本次创建的进程。
失败报告保留 `ok=false`，保存收敛进度、错误及节点日志尾部。

底层配置为三叉树，每个非根节点只填写父节点的地址和公钥；邻居上限等于树中该节点的度数。
所有名额均由必要边占用，避免测试发流量后退化成全连接。检查：

- 每个节点都发现全部成员并完成 IPv4 声明；全部 IPv4/IPv6 地址唯一。
- 每个节点的实际邻居集合与配置生成的树完全相等，总边数始终为 N−1。
- 每个进程都发起一次 8192 字节逐跳加密回显，目的在树的另一部分。
- 双向主动 trace 的节点身份序列精确匹配实际树路径，不只检查“complete”。
- 稳态窗口逐轮检查所有节点的成员数、邻居集合、boot ID；记录逐进程 RSS、CPU ticks、线程及 fd 数。
- 正常结束使用 SIGTERM，所有进程退出成功；失败时也逐个回收已拥有的进程。

## 百节点实测

接口事件驱动轮，本地二进制 SHA-256：
`33c0063aeda72958b887f96d9d269de929018fc1a703859c6ad9795ff9e10ee8`。
`target/daemon-scale-100-before-gossip-pacing.json` 已通过：100 个真实 daemon、99 条边，启动至全网发现约 1.11 s；
100 次加密回显全部成功，最慢约 273 ms，双向主动 trace 各 5 跳。
随后约 65 s 保持全体成员和必要边，跨越 60 s 记录 TTL 与空闲回收周期，无节点重启。

此窗口测得 100 个 daemon 合计 CPU 约 230.5%（一个逻辑核为 100%），单节点中位数约 2.12%；
结束时 RSS 合计约 793.0 MiB，单节点最大约 8.31 MiB，最大 fd 数 12。
这些是同机运行观测；CPU 不含启动/收敛和初始加密业务阶段，主机同时运行基础 netns 回归。
没有绑定 CPU 或独占主机，不将这些数值写成普遍性能保证。

本测试关闭 TUN，只证明进程、控制面与实际加密多跳数据路径。
它不替代百/千节点真实 TUN、持续应用负载、NAT、分区合并、并发故障或长时间资源稳定性验收。
千进程结果单独报告，不从百进程结果或内存图测试外推。

## 千进程旧版本负向证据

同一二进制与夹具实际启动了 1,000 个 daemon，使用 999 条配置树边；不是只生成 1,000 份配置。
`target/daemon-scale-1000-before-gossip-pacing.json` / `.log` 保留失败结果：180 s 收敛窗口结束时，
各节点可信成员数范围为 121–575，未达到所有节点均发现 1,000 个成员的门槛。
中间采样曾达到部分节点 744 个成员，随后回落，故不是只需多等几秒的单调启动过程。
尚未进入本轮全体加密回显、trace 和 65 s 稳态验收，`ok=false`；所有 1,000 个自有进程已回收。

保存的节点日志中，375 个节点出现 `control signature verification rate`。
旧版本发送端每个 tick 每邻居可发送四份记录，而接收端每邻居只接纳每秒 256 次控制签名校验；
启动/周期更新的突发可能消耗整个接收窗口。旧待发集合按 NodeId 排序取首项，
也存在持续重新加入低序键时抢占其他记录发送机会的风险，而不是通过提高验签上限掩盖突发问题。

### 记录传播修复

记录发送改为每邻居至少间隔 5 ms（最多 200 份/s），不累计空闲发送额度，也不在事件循环停顿后补发突发。
接收端原有每邻居每秒 256 次控制签名校验上限保持不变，为 trace 和到达抖动留出余量。
这只约束控制记录入链路的节奏，实际发送仍服从已有链路带宽与保护预算，不修改数据包/FEC/RTX 参数。

待发记录使用有界去重 FIFO：同一个身份只占一个位置，重复更新不改变其等待顺序；
发送时从记录库读取最新版本，避免排队的旧版本阻塞新状态。
新邻接先发送本机记录再传播其他已知记录；链路队列满时将该身份重新排到队尾，仍服从节流。
每邻居最多 4096 个待发身份，与记录库上限一致；断开邻接释放该队列。

普通回归覆盖重复更新的公平性、每秒发送上限、空闲后不突发、同 tick 不重试与 4096 项容量。
仅增加上述节流/FIFO 的二进制 `a802de8e03decf5dd58e825df96af0a237532f259802205549959797694a6492`
已实测 1,000 个进程：1,000 份节点日志均没有验签限流错误，但 180 s 结束时成员数仍只有 19–361，
记录为 `target/daemon-scale-1000-paced-only.json` / `.log`，全部进程已回收。
存档 `target/gossip-pacing-1000-live.json` 的前八节点样本包含多条降至 64 kbit/s 的链路及数千次队列丢弃。
这证明修复了第一处问题，不证明整项规模验收通过。

进一步将**无状态变化时**的周期重签从 5 s 改为 15 s（60 s 有效期的四分之一），
减少稳定全网的重复校验和发送负载。邻接、地址、成员策略或路由变化仍立即签发新记录，
候选来源到期在 100 ms 维护任务中独立检查，不等待周期重签。
记录 TTL、签名、序号、防重放、链路拥塞控制和默认 FEC/RTX 均不放宽。
这轮仍使用原来的千进程功能门槛复测；旧失败报告不改写为成功。

### 稀疏反向反馈回归

进一步把诊断扩展为完整 `Link`（真实 FEC/RTX、反馈队列与 pacer），发现：
正向每 5 ms 发送 900 字节、反向每秒一个字节，在双向独立 1–101 ms 抖动且没有网络丢包时，
反向心跳的正延迟差触发降速，而样本太少又没有提速资格；随后 ACK 队列反馈超时继续降速，
最终双向退到 64 kbps。`target/link-asymmetric-metrics-before.jsonl` 记录了决策计数：
1 Gbps 上限诊断在 120 s 时反向有 12 次延迟降速、831 次超时降速，正向只收到 7087 条消息。
这是确定性虚拟链路复现，不是千进程故障所有成因的证明。

新增常规回归使用 10 Mbps 上限，运行同类 120 s 负载并额外排空 1 s。
修复前 `target/feedback-regression-before.log` 为 14116/24000 条正向交付，
修复后全数交付（反向 120 条也全部交付）。修复为延迟趋势增加原始 ACK 的自适应置信门槛，
反馈超时要求仍有待确认源片；FEC 抑制不采用无置信度的旧梯度。
未提高初始/最低带宽、ACK 预算、重传次数、保护额度或千节点验收时限。
增加延迟/丢包/超时/探测速率决策计数、采样字节数和两类队列长度，便于区分降速原因。

该诊断在 120 s 截止时仍有在途消息，没有排空；全部交付断言由上述常规回归承担。

设计参照：[RFC 9002 §7.7](https://www.rfc-editor.org/rfc/rfc9002.html#section-7.7)
将纯 ACK 与普通数据 pacer 区别对待，以避免反馈延迟。nnlan 不是 QUIC；这只提示需要检查
本实现反向反馈与自身数据 BWE 的耦合，不表示已采用 QUIC 的规则，亦不取消认证、反馈队列上限
或实例级线上带宽预算。当前生产实现仍沿用有界 ACK pacer。

另外用有限的启动调度停顿扩展虚拟 Link：前 10 s 随机出现 30/100/300/500 ms 停顿，
随后恢复 1 ms 轮询；每 15 s 启动非对称数据突发，并保留每秒心跳。
正常 MTU 和固定 548 字节 UDP 上限各四组，共八组。
大停顿会造成启动期有限丢弃，但八组最后 60 s 的消息均交付，未复现永久 64 kbps 退速。
证据是 `target/link-startup-stall{,-small-mtu}.rs` / `.jsonl` / `.log`。
该有限模型不包括多邻居、实际 socket、持续调度抖动、并行会话或 PMTU 探测；
下一步仍需要真实 UDP / 多链路诊断，不能单凭这八组排除那些因素。

还发现一个应独立验证的 PMTU 线索：`target/crossed-rekey.rs` / `.json` 使用真实 Crypto
完成同时双向换钥，两个方向可以合法选用不同的活动 session（都保留对方的有效接收 epoch）。
当前 UDP PMTU 分支却在区分 Probe/Ack 之前要求收到的 session 等于本机活动发送 session。
由源码推断，这可能让对方仍在使用的有效接收 epoch 上的 Probe 得不到回应；
本轮根节点的一条链路也出现了 24 次探测、0 次确认、保持 548 字节的状态。
两项证据尚未构成实际 UDP 的因果验证，更不是千节点初始退速的证明。
下一步应补充交叉换钥的真实 UDP 探测回归，并保持已有“旧 epoch 的 ACK 不改变当前路径 MTU”负向断言。

### 交叉换钥的 PMTU 回归

上述 PMTU 线索已用真正的 UDP socket 重现：常规测试按 HS1 → HS2 → HS3 的交叉顺序交付，
两侧均选择对方发起的会话作为最后完成的活动发送世代。修复前，两端的认证 Probe 都被错误忽略，
2 s 内始终不能确认基础 MTU；`target/crossed-pmtu-before.log` 保留失败。
修复只区分 Probe 与 ACK：保留的有效接收世代可回复 Probe，只有当前活动发送世代上的 ACK
才有资格修改当前路径 PMTU。端点验证、AEAD、有限密钥寿命、线上总预算及旧 ACK 负向测试不变。
同一测试还要求两方向恢复到 1232 字节，并在不同活动发送世代上各交付 8192 字节消息。
普通测试中该回归通过，另外重复运行 20 次全部通过；`target/crossed-pmtu-repeat.log`。

规模夹具增加 `--verify-rekey`（至少 125 s 稳态）：通过只读 `key_epoch` 状态确认全部有向邻接
真实换钥，给握手后的探测最多 10 s 恢复时间；最后再做全体加密回显和双向 trace。
`make scale-rekey` 默认使用 100 节点与 135 s 稳态。旧的发现/地址/边数/无重启门槛不放宽，
也不更改产品的 120 s 换钥定时器。交叉换钥修复不等于初次千节点收敛已经通过。

### 真实换钥后数据门槛发现的第二个缺陷

PMTU 修正版 `17b32ecd9f7e0a4b80b1bb4b3958beb9e88bd3eb80e3fc266082cec6e0dd15bc`
通过 112 项普通测试与真实 TUN PMTU 专项（`target/e2e-crossed-pmtu.json`）。

## 真实 TUN：碰撞合并、分区恢复与中继重启

```sh
nix develop --command make scale-tun
# 改变规模时保留同一套完整门槛；上限 1000，开发用最小规模 7。
nix develop --command python3 tests/scale/tun_scale.py --nodes 100 --output target/tun-scale-100.json
```

每个节点拥有独立 network namespace、真实 TUN、身份与持久状态。底层按三叉树用
点对点 veth 连接，不安装宿主路由、桥接或 IP 转发；通信必须穿过覆盖网络的实际中继。
所有邻居名额由必要树边占用，不能靠发流量后全连接掩盖多跳问题。

测试依次执行五个阶段：

1. 先切断 0–1 边，再启动两个独立分区。0 和 1 使用公开碰撞测试身份，在各自分区都分配到
   `33.168.136.153`，证明是真正的分别分配后合并，而不是启动时就看到全网冲突。
2. 恢复底层链路，要求全网收敛、所有地址唯一、碰撞败者重新选 IPv4，IPv6 不变。
3. 再次断链，要求所有节点的已发现成员与实际邻居准确收敛到各自分区；双向跨分区 IPv4/IPv6
   探测必须失败，而每个分区内部全部节点仍能通信。
4. 恢复链路，要求重新发现全网，IPv4/IPv6 分配保持不变。
5. SIGKILL 碰撞败者（它也是中继），重新启动同一身份与持久状态；要求只有该节点 boot ID 变化，
   probe 持久值正确、地址不变、全部节点恢复通信。

每个阶段都对**每个节点**执行两个地址族的 3 次完整 1280 字节 IP 报文回显（16 个并发 worker），
以及逐节点主动 trace，精确核对实际树路径。要求每次回显全部收到，不以比例通过；
检查每个 TUN 的实际双栈地址、每个分区内地址唯一、地址池正确、默认 relay 开启和确切邻接集合。
每阶段有独立 180 s 收敛期限，任何一次流量失败保留该轮失败，不自动重试抹去结果。

结果包含二进制/夹具哈希、逐阶段状态、逐项 ping 原文与 trace、失败日志尾部和自有进程/namespace
回收状态。夹具自身的 Python 测试验证分区覆盖、非跨区路径、重复地址的作用域和零丢包门槛。
这不是吞吐、千节点 TUN、长期 churn 或所有并发故障的完成证明；实际规模结果单独列出。

这是单轮同机百节点内核功能验收，不宣称千节点、吞吐、长期 churn 或物理网络验收完成。

### 静态底层复测与逐路由子进程

6252 构建的 `target/tun-scale-100-static.json` 五阶段通过，全部资源回收；
`target/tun-scale-1000-static.json` 在核验全部 1998 个永久邻居项后仍失败。
最后一批观测结束于 214.170 s（失败的 RPC 批次越过 180 s 截止线，未按成功处理），
987 个有响应的节点成员数为 1–183；尚未进入流量阶段。所有进程及 namespace 已回收。
这证明修正 ARP 容量并不足以解决千节点问题。

在该轮选择 16 个自有 daemon、连续 100 次读取其 `/proc` 子进程，记录到 434 次 `ip`
子进程观测，包含 TUN 路由增加与删除；原始证据为 `target/tun-scale-static-process-samples.json`。
源码中的 `Tunnel::sync_routes` 每条路由同步启动并等待一个 `ip` 进程，会阻塞同一 Engine
中的收发与管理 RPC。采样次数不是 CPU 占比，不能把它当作总体加速比。

现将这一条高频路径改为每 TUN 一个持久 rtnetlink socket，直接增删 `/32` 和 `/128` 路由，
每次收到匹配的内核 ACK 才更新本地集合。保留 exclusive add、不替换已有路由，删除限定
接口/协议/前缀；socket 收发有超时，内核错误继续使操作明确失败。不新增依赖、路由管理框架
或后台队列，初始化地址及 Subnet/Exit 策略操作不在本次变更范围内。
实现格式依据 [Linux Netlink 文档](https://docs.kernel.org/userspace-api/netlink/intro.html)
和 [rt-route 规范](https://www.kernel.org/doc/html/latest/netlink/specs/rt-route.html)。

`make e2e-tun-routes` 在独立 namespace 中核对两个地址族的增加/删除、已有路由不覆盖、
其他接口路由不删除、重复操作的内核错误，以及 2000 条真实主机路由的完整增删 ACK。
普通测试另外覆盖报文格式、截断/错序 ACK 和内核错误传播。新构建的规模结果独立归档，
不将旧构建的百节点成功沿用为新构建验收。

#### ping 计数混杂因素，失败结果保持不变

夹具使用 `ping -c 3 -i 0.1 -W 2 -w 5`。在所用 iputils 中，设置 deadline 后不会在
发送第三包时停止发送，而是在收到足够回复后结束；高 RTT 下，退出时尚在途的额外包也会
进入其 loss 汇总。依据 [iputils 20250605 的 pinger 实现](https://github.com/iputils/iputils/blob/20250605/ping/ping_common.c)。

隔离双节点、仅增加每向 150 ms 延迟、不启动 overlay 的对照也复现：双栈均报告发送 6、
收到 3；去掉 `-w` 后均为发送 3、收到 3。原始输出、版本和清理记录见
`target/ping-deadline-diagnostic.json`，诊断脚本 `target/diagnose-ping-deadline.py`。
因此这轮 2000 次 ping 中的 284 次计数检查失败不能全部判作实际丢包；其中 1999 次调用
仍观察到了序号 1、2、3，另一次只收到序号 21、22、23，需要继续调查。

本轮没有改写既有验收条件或把失败转为通过。下一轮应先将探测改为严格固定发包数、
由外部超时限制总时长，并保留逐包零丢失检查，再结合控制传播与队列延迟诊断处理真实尾延迟。
4 次精确 trace 失败独立于 ping 计数问题，仍必须解决。机器可读分析见
`target/address-index-scale-analysis.json`；继续采用千级精简链路状态架构，不引入 DHT，
不提高验签限额或延长记录有效期来掩盖压力。
