# 当前传输实现

这是 nnlan 的覆盖网络实现选择，不承诺复刻 UU、WebRTC、CM256 或 WireGuard 的线上格式。
产品范围仍以 [project-decisions.md](project-decisions.md) 为准；已接入真实组网 daemon，子网/出口等剩余验收见实现状态。

## 格式能力扩展

GGB3 的认证 INTERNAL 控制消息显式交换能力版本 2，按密钥世代保存；旧节点保持旧格式。
协商后直连 DATA 从会话恢复身份，单片源帧省略可推导字段，批量 ACK 使用无损基值/偏移编码。
接收统一回到原 Envelope/Fragment/Ack，继续共用成员/IP 来源验证、重放、FEC、路由与预算。
多跳/trace 保留完整身份，旧世代不替新世代证明能力。详见 [紧凑数据](compact-data.md)。

## 数据路径

daemon 使用 Tokio current-thread executor：主要网络状态本就由同一个 Engine 顺序拥有，
管理、DNS 和接口观察继续作为异步任务运行，不为每个实例另建两个调度 worker。
这不把密码/FEC 移到后台线程，也不新增线程池或跨线程数据队列。
具体 I/O/定时器驱动与任务执行语义见 [Tokio runtime](https://docs.rs/tokio/1.53.1/tokio/runtime/index.html)。
性能影响以实际双栈 TUN、规模与部署测试为准，而非仅按线程数量推断吞吐。

```text
TUN / echo → Envelope（声明源身份、目标身份、跳数、业务载荷，无内层密文）
  → Message（独立报文，最大 32768 字节）
  → 分片、原始序号、2 ms / 8 源片封组
  → GF(256) Reed–Solomon parity
  → 反馈 / 共享保护预算 / Burst AIMD pacer
  → 每次发送使用新 nonce 的 Noise AEAD
  → UDP

UDP → AEAD + 8192 包重放窗口 → 有界 FEC / 重组 → Message
```

相邻链路使用 `Noise_XX_25519_ChaChaPoly_BLAKE2s`，由 `snow` 实现。
Ed25519 身份签名绑定每个进程的 Noise 静态 DH 公钥；prologue 同时绑定协议、scope、
会话编号和双方身份。入站不要求事先登记公钥；出站验证预期公钥。
新会话拥有独立发送序号、重放窗口和 Link 实例。仅保留逐跳 scope=0，非零 scope 被拒绝。
中继可读取完整 Envelope 载荷，按覆盖目的身份转发；没有第二套加密、握手或待发队列。
GGB3 的完整信任与迁移语义见 [单层加密说明](hop-encryption.md)。

密钥世代不是拥塞路径：相同的认证远端端点及本地源地址共用一份 `Controller`，
由 UDP 的 Peer 直接拥有，无引用计数、互斥锁或跨线程共享状态。
新旧 Link 只持有各自的 FEC、源片缓存、重组、反馈队列和时间戳原点；
显式借用同一控制器进行调度和记账。每个 UDP tick 合计所有保留世代的排队量和待确认状态，
只维护一次路径估计器。换钥既不重置带宽估计，也不复制 pacer token、控制额度或保护债务。
认证端点变化时重建路径控制器；从新端点重新握手或完成路径挑战时，清理旧路径的 Link。
本地源地址变化同样重置估计和每个保留世代的反馈时钟。

ACK 的发送/接收时间均相对其密钥世代，故梯度和趋势窗口仍各世代独立；
禁止把两个世代的时间戳交叉相减。只有新的完整趋势窗口更新路径拥塞信号，
新世代的首包不清除已有过载证据；超过 1 s 未更新的趋势信号过期，避免退役世代永久阻止恢复。
`status.neighbors[].link.control` 表示路径级累计控制状态，其余 Link 计数仍属于当前发送世代。

数据面 Envelope 解码按完整 32 字节公钥在现有成员集合中查询，复用已验证的 `NodeId`，
避免逐 IP 包重复做 Ed25519 点解压。查询未命中仍走原有公钥校验，不新增身份缓存或扩大成员集合。
这只是解析优化：前一跳和声明来源的当前成员资格、逐跳认证、IP 来源/发布者绑定仍分别检查；封禁/撤回后的记录
不会因曾经命中过解析路径而继续获得资格。严格解码、任意字节/弱公钥、身份错配与撤回有回归测试。

握手每 400 ms 重试、8 s 清理；初始报文填充到 280 字节，避免响应放大。
单一逐跳 Crypto 每秒最多接收 32 个新握手、最多 64 个未完成握手。
候选允许每身份两条主动、两条被动握手；这些单身份上限共享全局 64 条上限。
这不是完整的无状态 cookie 抗洪泛方案，仍需后续攻击流量压测。

UDP 适配器统一执行入站/出站邻居名额和配置 peer 预留。1 s 保活、6 s 无认证活动断开；
120 s 触发换钥，逐跳旧接收会话空闲超过 30 s 后清理，密钥绝对寿命 300 s。
每个 peer 最多 4 个世代，总会话最多 8192；容量紧张时，仅在新握手证明身份后淘汰最旧非活跃世代。
未认证的请求不驱逐已有密钥；频繁路径迁移不再依赖邻接超时腾出世代名额。
端口变化先验证加密 challenge/response，再更新路径并建立新密钥/FEC 世代；
路径切换期间旧组和在途报文可以丢弃，不保证 IP 报文可靠交付。
观察地址经已认证邻居返回；候选随签名记录交换，实际流量触发有界交错直连尝试，
具体握手取消与需求过期规则见 [候选生命周期](candidate-lifecycle.md)，实测范围见 [Linux NAT 验收](linux-nat-testing.md)。

## FEC、反馈与资源边界

`[repair]` 的 `fec` / `rtx` 独立控制本机发送修复，均默认开启；接收支持、反馈和拥塞控制不关闭。
四模式实测与精确帧级负向对照见 [弱网矩阵](weak-network-testing.md)。

- 当前 codec 为 `reed-solomon-erasure` 的 GF(256) RS，编码矩阵按 `(K,M)` 缓存。
  不是 CM256 字节兼容实现，也不是 RTP ULPFEC/FlexFEC。
- 源片最大宽度随逐跳 PMTU 为 489–1393 字节，原始发送省略零填充；单片业务载荷上限为 466–1370 字节。
  parity 只补齐到本组最长源片（最低 489），不把未使用的路径容量全部补零发送；见 [开销优化](protocol-overhead.md)。
  原始包立即进入调度，不等封组；最多 K=8、M=4，稀疏组最长等待 2 ms 才产生 parity。
  原文 K=109 是媒体上限，不强制本实现等待 109 个包。
- 原始发送、FEC 恢复、重传到达分开反馈。ACK 携带原始包号、发送时间、接收时间和到达类型；
  时延梯度只比较两端各自的时间差，绝不相减两台主机的绝对时间。
- 丢包反馈驱动冗余比例：`ceil(K × (p/(1-p) + 0.1))`，受 M 上限及保护预算约束。
  这是覆盖网络的适配公式，不将原文未知参数推断标为已证实。
- 初始 BWE 8.1 Mbps；300 ms 快速采样窗，至少 200 ms / 12000 字节才更新丢包估计。
  RTT、时延梯度、排队和反馈中断共同参与速率更新。
  时延差保留乱序造成的负向变化；没有新的完整趋势窗口时，不反复使用旧趋势降速。
  原来的相邻包差分 EWMA 仅保留为诊断量 `delay_gradient_us`，不再直接触发降速。
  低速恢复采用单独的 ACK 门槛 `clamp(rate_bytes_per_second × 0.2 × 0.5, 1000, 12000)`，
  仍要求 200 ms 观察跨度和新的实际 ACK；过期丢失样本不作为提速证据，丢包估计的 12000 字节门槛不变。
  延迟降速也要求相同自适应字节门槛和时间跨度，但只统计原始到达：
  单个心跳的抖动、FEC 恢复或重传不能建立延迟趋势的置信度。
  缺少置信度的旧梯度不触发 FEC 抑制，也不阻止迟滞恢复。
  反馈超时只对仍有待确认源片的排队链路降速；纯 ACK 队列不等待 ACK 的 ACK。
  空闲后新产生的源片重新开始反馈等待计时，不沿用空闲之前的最后 ACK 时刻立即降速。
  所有反馈仍受链路总 pacer 和实例总预算约束。反馈额度在每次维护间隔内取
  `max(估计发送带宽 × 间隔 × 10%, 已认证且成功处理的数据帧线上字节 × 10%)`，
  两项不相加，桶上限仍为 2400 字节；接收额度被取用后清零，没有空闲累积收益。
  只有 Source / Parity / Seal 提供接收额度，ACK/NACK 或处理失败的帧不提供，
  避免“反馈为更多反馈提供额度”的循环。接收快流量不提高本方向数据 BWE 或总 pacer。
  这是对旧“仅按本方向发送 BWE 的 10%”规则的修正：交叉换钥或单向业务中，
  接收世代可能只产生反馈，没有反向业务源片来提高它自己的 BWE，旧规则会饿死 ACK。
  普通回归覆盖无反向源片的 115.2 Mbit/s 提供负载，以及不提高总额度、不重复消费接收额度等边界。
  总 pacer 仍可能限制更高的单向负载，不能由这一测试外推任意吞吐。
  同一发送方向的反馈队列与业务/修复队列轮转：两者都具备发送额度时交替取包，
  任一队列空闲或暂时没有额度时不阻塞另一队列。只在真正发包后切换次序，
  不因清理过期项而丢失轮次。避免繁忙接收方向的 ACK 在每次延迟唤醒时抢光
  2400 字节初始 burst，使反向原始源片在 250 ms 内一次也发不出去。
  这不是绕开反馈速率限制或扩大 burst；普通回归覆盖 20 ms 调度间隔、8192 字节业务、
  两端完整 Link、548/1452 字节 PMTU 与逐包/批量 poll，反馈和业务均须继续交付。
  随机丢包不单独触发退速；持续严重丢包加队列压力仍退速。
- FEC / RTX 共用 500 ms、最多估计线上预算 35% 的保护额度，计入 UDP/IPv6、加密头/tag。
  FEC 最多占保护额度 80%，保留 RTX 空间；早期 RTX 可借用剩余额度形成可观察债务，
  晚期 RTX 在有债务或队列过长时拒绝。借用不突破共享上限。
- 拥塞/排队压力持续 2 s 抑制 FEC；恢复条件持续 5 s 后重新启用。
  原始、修复和 ACK 均受 pacer 约束；ACK 另有速率上限，实例级总预算采用轮转调度。
- 最多重传两次，源包缓存寿命 1 s；发送队列最多 2048 项；源包缓存按带宽时延积在 2048–16384 项间调整，
  全部邻居/世代共用 32768 项源片上限，详见 [准入背压](backpressure.md)。
  接收 FEC 组和重组消息各 128 项、1 s 超时；ACK、握手、路径挑战都有数量或时间界限。
  邻居状态的 `unsent_sources_dropped` 单独统计已入队、但第一次发送前因排队期限或 MTU 变化
  被丢弃的源片；不把被保护预算拒绝的 parity/RTX 误认为业务源片丢失。
  源片排队最多 250 ms；组结束标记 Seal 与组中最早源片共用排队截止时间，
  不在源片全部过期后继续以原来 1 s 时限占用 pacer。否则持续超量入队时可能只发送孤立 Seal，
  把配置带宽全部耗在没有业务价值的分组标记上。缓存/RTX/接收组的 1 s 寿命不因此改变。
  重传因保护预算或排队时限被拒绝后，等待一个 RTO 再尝试排队；NACK 不跳过该退避，
  也不延长原有源缓存寿命，避免对同一过期重试逐 tick 反复排队/拒绝。
- UDP payload 上限 1452 字节，先确认兼容档位 1232；实际发送大小由认证探针动态确认，支持下降、黑洞探测和恢复增大。
  独立方向、FEC 封组、反馈拆分及 ICMP 处理边界见 [逐跳路径 MTU](path-mtu.md)。

参数中，500/300/200 ms、12000 字节、35%、2/5 s 与 8.1 Mbps 参考
早期参数与拥塞控制研究笔记（未随公开仓库发布，不是构建输入）；
分片大小、K/M、2 ms、队列容量、RTX 次数、AIMD 增减系数等为本项目明确选择，仍需性能实验。

### 延迟趋势估计

`link/delay.rs` 按发送时间把原始 ACK 合并为至少相隔 5 ms 的组，只保留 20 个完成组；
接收间隔不超过 5 ms、短于发送间隔且组内接收跨度小于 100 ms 的压缩突发继续合并，
避免一次调度唤醒排空积压时，在同一个接收时间上制造许多趋势样本。
每组取最后发送时间与最大接收时间。旧发送组的迟到 ACK 不改写当前组。两端各自减去固定原点，
得到累计延迟差；对其做 0.9 系数平滑，再以接收时间为自变量做中心化最小二乘回归。
不能照搬研究文档中明确标注为推断的“以平滑延迟为自变量”伪代码。

算法参考 [WebRTC TrendlineEstimator](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/congestion_controller/goog_cc/trendline_estimator.cc)：
趋势分数为 `slope × min(samples, 60) × 4`，阈值初始 12.5，在 6–600 范围内自适应。
超过阈值需要多组、超过 10 ms 且斜率不再下降，才确认过载；尖峰不用于抬高自适应阈值。
同时保留原来的字节/时间置信门槛、反馈新鲜度、有限保护预算和反馈超时退速。
`delay_trend`、`delay_threshold`、`delay_overusing` 可从邻居状态观察。

5 ms 聚合参考 [InterArrivalDelta](https://webrtc.googlesource.com/src/+/refs/heads/main/modules/congestion_controller/goog_cc/inter_arrival_delta.cc)
的发送时间组/接收突发合并思想，但这里不是其 RTP 分组实现：本协议反馈可能按序号而非到达顺序排列，组内采用最大接收时间，
保留有符号的组间差。发送间隔超过 1 s 时重新预热，避免跨空闲保留旧趋势。
每个 ACK 的组内更新为常数时间；完整回归最多约每秒 200 次、每次 20 点，不随 PPS 线性增加回归次数。

### 一次定时维护，多轮公平发送

UDP 调度器仍每轮每链路最多取一个包，且保留实例总预算与每 tick 256 包上限。
同一个 tick 使用同一 `Instant`，Link 仅在该时间点首次 poll 时扫描源片缓存、处理定时维护和更新控制器；
后续轮次继续逐包执行真实 pacing/保护预算、扣款、过期队列与 nonce 分配，不重复扫描缓存。
普通回归对比逐包轮转与批量 poll 的完整报文序列，并检查超时/队列回收仍然生效。

## 已有验证

### TUN 边界批处理与按需唤醒

TUN 使用 `tun-rs` 的 GSO 分段和 GRO 合并；内核聚合上限 65535 字节、128 段，
读端保留跨轮未处理尾段，写端最多 32 包并在本轮事件结束时提交。
每个 IP 包仍独立做来源/路由校验并进入原有 GGB3、FEC/RTX 和逐跳加密路径。
单片消息避开重组分配；发送缓存源片直接编码，固定三次发送时间戳内联保存。

批处理减少了 I/O 事件，不再假设其他收包总能及时驱动下一次发送：
原有 1 ms 维护和 250 μs I/O 泵之外，用单个按需 timerfd 唤醒不足 1 ms 的待发机会。
预测不扣款、不产生新额度，实际发送仍走原来 poll/charge 和公平调度；空队列撤销唤醒。
没有新增工作线程或扩大协议队列。TUN 的 500 条队列未调大，但每条可承载聚合包，
因此字节积压可能增加，过载背压仍有待改进。实现、资源边界与对照见
[TUN 批处理性能记录](datapath-batching.md)。

## 逐跳密钥就绪与 GGB3

当前线格式为 `GGB3`，Noise prologue 为 `ggbond.noise.v3`；不与 GGB1/GGB2 节点混用，
也不做自动降级。身份、公钥和地址派生不变。版本隔离保证旧节点不会误用新增确认报文的 nonce 语义。

Noise XX 的 HS2 只让发起方取得本地传输密钥，对端仍须收到 HS3。
现在发起方把该密钥放入有界待确认集合，换钥期间继续使用旧的已就绪发送密钥；
首次连接尚无可用密钥时，不发布已连接事件；业务走其他可用多跳路径，无路径则明确失败，不创建端到端握手缓存。
收到 HS3 的响应方安装密钥并返回 `READY`（kind 8）。它是新传输密钥下固定域
`ggbond.key-ready.v1` 的 AEAD 证明，不是明文 ACK。

- READY 专用 nonce 为 `u64::MAX - 1`；DATA 只允许更小的计数。Noise 的 `u64::MAX`
  保留给其 rekey 原语，不用于本控制报文；参见 [Noise CipherState](https://noiseprotocol.org/noise.html#the-cipherstate-object)，
  并已核对锁定的 snow 0.10.0 实现。READY 不进入业务重放窗口，改写报文 kind 无法推进该窗口。
- READY 丢失时发起方每 400 ms 重发缓存的 HS3，响应方重发原字节的缓存 READY；
  不重复加密同 nonce 的不同内容。整个过程仍受从 HS1 开始的原有 8 s 握手期限约束。
- 未完成 Noise 和待确认密钥共用 64 条上限；每身份主动候选仍最多两条。
  到期和取消清理临时密钥与缓存，重试等待仍计为 pending，避免旧密钥超龄后逐 tick 发起新握手。
- 合法 DATA 可以先于 READY 到达，作为隐式就绪证明：逐跳在解密/重放记账之前检查原握手端点。随后建立对应 Link 并处理同一报文，不丢弃首包。
- 以本地单调完成序号比较密钥新旧，不用易重合的时钟值排序；迟到的旧 READY 不回滚已就绪的新发送密钥。
  同路径同时打开的接收世代保留，其他候选端点的未确认密钥在选出成功路径后取消。
- 每条邻接链路使用同一就绪机制。READY 重复到达不会再次发布连接事件或重建 Link。

单元回归覆盖 HS3 暂存时旧密钥业务继续交付、READY 与 DATA 乱序、端点错配、
认证失败、类型改写、nonce 边界、丢失两类确认、原始期限、64 条共享容量及迟到确认。
这不是省略握手确认或增加无限可靠重传层；业务 FEC、RTX 与队列寿命均保持原有边界。


## 认证状态提交与会话编号隔离

一次 UDP 接收使用调用方持有的局部事件列表。认证已导致连接状态提交后，后续载荷解析失败
仍计入 `invalid_udp` 并丢弃畸形载荷，但不抹去已经产生的 Connected 通知。
握手完成后也先同步邻居/Link 与通知，再发送缓存的 READY；本地发送错误不留下
“密码层已连接，运行时却未收到接纳通知”的半完成状态。列表只属于这次接收，未新增后台事件队列。
认证失败仍不接纳节点，畸形载荷也不回滚防重放状态；重复 READY 不再发布连接通知。
真实 daemon 回归要求在暂存 READY 的情况下，收到首个畸形认证报文后实际发送自身节点记录，
而不是只检查 UDP 内部 `has_peer` 标志。

会话编号是公开的 64 位随机索引，不是身份凭据。新 HS1 不得使用任何仍存在的传输密钥编号，
即使较短的完成握手缓存已经过期。检查发生在新握手状态和接纳速率记账之前，适用于全部逐跳会话。
否则另一身份的有效握手可能覆盖该编号下的密钥，而旧身份的 active 索引仍指向它。
回归使用三个真实身份复现旧行为，并验证冲突被拒绝、原身份通信不变、对方用独立编号仍能正常建连，
以及两条会话相互解密失败。没有修改线格式、身份准入规则、FEC/RTX、时限或路径预算。


### 2026-09-24：缓存维护快速判断

源片序号与创建时间单调，`last_sent >= created`。最老源片年龄尚小于 `min(RTO, lifetime)` 时，
跳过该轮缓存全表扫描；封组先执行，ACK/NACK、1 ms 维护与有限 RTX 时序不变。
本轮最终保留版没有扩容 2048 项缓存，也没有更改 TUN 参数；扩容候选与队列试验的取舍及
性能/交付数据见 [高 RTT 记录](high-rtt.md)。


### 2026-09-26：缓存容量与 TUN 准入

待确认保留空间按速率/RTT 调整，并由实例共享 RAII 源片额度兜底；队列硬上限不增大。
本机 TUN 在软工作量水位或缓存容量不足时保留未消费的读批次，让 ACK/pacer/管理继续运行，
空间释放后重新校验当前策略/路径再发送。停滞 20 ms 或批次绝对寿命 250 ms 后明确丢弃，
避免冷启动正常 GSO 进展被误判为无进展，也避免黑洞无限占住单 TUN。
高 RTT 吞吐与交付改善，满载尾延迟尚未解决；边界与完整正负结果见 [背压记录](backpressure.md)。


### 2026-09-26：TUN 快速读取与流队列

后续实现用实例共享的有界 ingress 流队列替代上节暂停整个 TUN 分支的方案。
每轮跨就绪聚合快速读取最多 4096 段/500 μs，再按 256 个哈希流桶做新/旧流 DRR、
调度及链路准入；一个目标受阻不再直接关掉所有 TUN 读取。
硬界限为共享总量 32 MiB/32768 包、准入前绝对寿命 500 ms，按需分配；
无额外单桶字节限额，满时从最大桶丢弃，原有源片准入后 250 ms 未发期限保持；
仅在硬容量/绝对期限触发时丢弃；试验中的 CoDel/ECN 提前信号因吞吐代价未保留。
待确认源片额度、加密、线上格式、FEC/RTX/保护预算保持不变。
具体边界、字段语义、吞吐/满载 RTT 对照及中间失败版本见 [排队记录](queueing.md)。
