# GGB3 紧凑数据与小包处理

后续高 RTT 的缓存扫描优化及扩容/队列试验见 [高 RTT 记录](high-rtt.md)；本文保留本阶段数据。

2026-09-23。基于上一轮大包探测/FEC 按组填充版本，保留单层逐跳认证加密、FEC/RTX、
默认 TUN MTU、队列条数/寿命和原带宽预算。本轮不调整 FEC 比例。

## 显式能力交换，不另建一套数据面

既有认证 Link 消息的 INTERNAL（kind 0）增加 `[2, 2]` 能力请求和 `[3, 2]` 确认。
版本 2 表示同时支持紧凑单片源帧、直连 DATA 隐式身份和无损批量 ACK 压缩；未知版本/操作码不生效。
未收到能力证据时，每秒既有心跳机会发送一次请求，依旧经过有限 FEC/RTX、队列和预算。
旧 GGB3 会忽略这两个操作码，双方继续用旧格式；不是根据 PMTU 大小猜测协议能力。

能力属于具体认证密钥世代，不从旧世代、节点公告或地址迁移继承；新世代重新交换。
交叉换钥时请求在收到它的世代确认，不借用另一活动世代。收到有效请求或确认才允许
该世代发送新格式。接收实现始终支持两种格式：请求与确认可能重排，收到新格式仍须先
通过同一层 Noise 认证/重放检查和原有成员/路由验证，能力位不是成员接纳条件。
`neighbors[].link.compact` 反映当前活动发送世代已收到能力证据。

能力请求使用既有 1 s 心跳机会，不给每个源包另加协商状态。首次连接/换钥到确认之间暂用旧格式；
因此不能保证高 PPS 纯 UDP 在该窗口仍具有稳态压缩后的容量。本轮自然换钥负载为 TCP+ICMP，
纯 UDP 成本/丢包测试为不跨换钥的稳态窗口；即时随握手发送能力声明和纯 UDP 换钥专项留待后续。

## 三项省字节的改动

1. **直连 DATA 省掉 66 字节 Envelope 头**：仅当起点是本节点、终点是下一跳邻居、
   kind 是 DATA 时，使用 Link message kind 3，载荷仍为原 DATA body。
   接收端从认证邻居恢复 source、本节点恢复 destination、hops 固定 1，转成同一 Envelope。
   接着共用来源 IP/子网发布者绑定、成员撤销和 TUN MTU 校验。中继转发、trace、trace reply
   仍发送完整 Envelope；没有短 ID 表、全网同步协议或绕开验证的第二条路径。
2. **单片源帧省掉 12 字节**：新增认证 Link frame tag 6，其余 Source 固定字段不变。
   省略片内 sequence（从 group + index 得出）及单片固定的 index=0/count=1；
   保留独立 message ID、实际长度和 kind。接收时还原成原来的 Fragment，再共用
   FEC、分片/消息重放和交付逻辑。多片源帧仍用 tag 1。

3. **批量 ACK 去重复高位**：tag 7 用 26 字节批头保存数量及序号/两种时间戳的完整基值，
   每项 11 字节保留序号偏移 u16、发送/接收时间偏移 u32 和 arrival 类型。
   32 条反馈从 802 降到 378 字节（不含外层封装）；不丢 ACK、不降低微秒精度、不改变恢复/RTX 语义。
   单条或偏移溢出时仍用 tag 4 完整反馈；解码检查长度、维度、arrival 与加法溢出。

RS 编码始终使用完整的规范 Fragment，parity 不采用这 12 字节压缩，因此混合新旧源帧、
源包丢失、校验片先到和重传都使用同一解码器。保留实际长度用于恢复后去填充。
每个缓存源片记住入队时选定的格式，能力升级不修改已排队/已发送源片；发送、反馈、
重传与丢失成本均按实际选定格式记账。没有通过少计字节或提高 pacer 上限提升数字。

最大可分片载荷/MSS 保持保守的原规则，不把压缩省出的空间偷偷用于增大未协商的 FEC 片。
默认直连单片数据源包合计省 78 字节；parity 只受 Envelope 缩短影响，组封闭包仍存在。

## 小包丢弃定位

仅实现前两项的 pilot 中，300 B/100 Mbit/s 仍接收约 85.33 Mbit/s，丢 14.67%。
新增有界日志明确显示 `link send queue full`；采样时发送数据队列为 0，但在途源片约 1750。
反向路径带宽估计仍为初始 8.1 Mbit/s，25 字节逐源片 ACK 加封装消耗完反向总 pacer，
反馈积压后源片缓存达到 2048 而拒绝新包。这不是 TUN 内核队列丢包。
本轮压缩反馈字节，不通过把反向估计值直接抬高或扩大源片缓存解决。
初始试跑使用的能力版本 1 不含压缩 ACK，最终显式使用版本 2，二者不误认为互相支持。

## 满尺寸 TCP 的预算预期

默认 TUN 1280、IPv4 TCP 含时间戳、8 个源片与 1 个 parity 时，应用载荷仍为每包 1228 B。
按现有 IPv6 IP/UDP 保守预算，原版每个源片 1477 B、parity 1470 B、seal 99 B；
新版对应 1399 B、1404 B、99 B。理想有效比例约从 73.40% 到 77.38%，
不是通过这些压缩就达到 90% 以上：校验片、内外层头和封组包仍真实消耗带宽。
这是该组规模/保护比例的预算模型，不是所有丢包条件或所有包长的吞吐上限。

### 正式配对：千兆整形、默认 TUN 1280

同机 Xeon Gold 5218 / Linux 6.18.46，64 个逻辑 CPU、不绑核；独立 network namespace，
双向 1000 Mbit/s 整形，BBR 单 TCP 流、FEC/RTX 开启。每次预热 20 s、测量 15 s，
满载期间 50 次/s ICMP；旧→新、新→旧、旧→新三轮，编译和其他网络测试不与测量重叠。
这是软件整形的同机对比，不是物理 NIC/公网/多机器吞吐；本轮没有重跑 WireGuard 对照。

| 直连 IPv4 | 原版 goodput Mbit/s | 新版 goodput Mbit/s | 原版 p99 ms | 新版 p99 ms |
| --- | ---: | ---: | ---: | ---: |
| 第 1 轮 | 723.85 | 763.57 | 4.15 | 4.12 |
| 第 2 轮 | 723.61 | 763.34 | 3.79 | 4.26 |
| 第 3 轮 | 723.78 | 763.37 | 3.94 | 4.03 |
| 中位数 | **723.78** | **763.37** | **3.94** | **4.12** |

吞吐约 **+5.47%**，但满载 p99 中位数增加 0.18 ms，没有把吞吐改善说成尾延迟下降。
新版单轮 IPv6 751.10 Mbit/s、p99 3.76 ms；反向 IPv4 763.62 Mbit/s、p99 3.81 ms。

额外路由 underlay 场景各只有一对样本，不是 overlay 多跳容量测试：

| Underlay 条件 | 原版→新版 goodput Mbit/s | 原版→新版 p99 ms |
| --- | ---: | ---: |
| RTT 20 ms，无注入丢包 | 587.90→595.24 | 67.2→64.3 |
| RTT 20 ms，双向各 1% 丢包 | 587.54→587.65 | 69.3→75.5 |

**高 RTT/丢包场景没有同等收益，1% 样本几乎没有吞吐改善、尾延迟更高**。
排队/背压仍是独立问题，未通过放宽测试阈值或删除这个样本掩盖。

六次直连均收到 750/750 ICMP、TCP 重传 0、TUN TX drops 0；两端通用 daemon dropped 各增加 1。
进程 CPU 中位数 A/B 为 70.06%/58.02%→71.19%/58.08%（100% 为一个逻辑 CPU），
不是绝对 CPU 使用率降低，而是在相近 CPU 使用量下交付更多数据。
IPv6、反向和两组 underlay 场景也均 750/750 ICMP、TUN TX drops 0、daemon dropped 两端各 1；
20 ms/1% 的 TCP 重传为 45→36，其余为 0。原始报告同时保留链路队列/FEC/RTX 计数。

### 固定 UDP 业务量

采用接收端 iperf 报告。字节比 = A 端协议记账发送字节 / B 端接收应用字节，
含 A 的修复/控制发送、不含 B 的反向流量；IP/UDP 按 IPv6 的 48 B 保守预算，即使 outer 为 IPv4。
它不是物理线路抓包字节，也不是 UDP 最大吞吐。各场景单轮配对，另保留高 PPS 超载试跑。

| UDP 应用载荷 / 提供速率 | 原版→新版接收 Mbit/s | 原版→新版丢包率 | 原版→新版 A 端字节比 |
| --- | ---: | ---: | ---: |
| 1200 B / 100 Mbit/s | 100.00→100.00 | 0%→0% | 1.34564→1.27375 |
| 300 B / 50 Mbit/s | 50.00→50.00 | 0%→0% | 2.03686→1.77684 |
| 300 B / 100 Mbit/s | **85.31→100.00** | **14.69%→0%** | 2.03678→1.77675 |

前两组零丢包对照的 A 端字节成本分别降低 **5.34% / 12.77%**。
反向反馈侧也有收益：1200 B/100 Mbit/s 的 B 端记账发送字节为 4568663→2535975，
300 B/50 Mbit/s 为 9084420→5031048，约减少 44.5% / 44.6%。
这些包括 B 的反馈、保活/记录等，不把它们全称为纯 ACK 字节。
300 B/100 Mbit/s 的 A 端 daemon dropped 从 91818 降到 1；两端 TUN TX drops 均为 0。
其余零丢包配对的 daemon dropped 两端各 1，源队列/未发源片丢弃与 RTX 均为 0。

**容量仍有边界**：新版 300 B 提供 200 Mbit/s 的额外单次压力测试，只接收 **162.67 Mbit/s**，
丢包 **18.66%**；A 的 daemon dropped 增加 233295，B 的 queue_dropped 增加 16、
unsent_sources_dropped 增加 1，TUN TX drops 均为 0。日志再次出现源片队列准入失败，
B 的发送记账约 8.1 Mbit/s，反向初始 pacer/反馈容量问题在更高 PPS 下仍会出现。
本轮解决的是已复现的 300 B/100 Mbit/s 情况，不是宣称所有小包都能跑满千兆。

所有正式报告在 `paired/`，TCP 汇总 `paired-summary.json`，UDP 汇总 `udp-summary.json`。
保留原版高 PPS 丢包、未加入 ACK 压缩的 pilot、以及新版 200 Mbit/s 压力结果；没有只保留好样本。

### 验证范围

- `build-v3.log`：fmt、Clippy `-D warnings`、179 项 Rust 普通测试、14 项 Python 测试及 release 构建。
  新测试覆盖单片压缩的规范还原/截断/非法索引/溢出、仅直连 DATA 可省身份、能力升级不改变已排队
  源片及精确字节记账、认证与未知能力版本/世代隔离、ACK 的精确时间戳/稀疏序号/arrival/溢出回退。
  原来长短组、丢最长/最短源片、parity 先/后到、禁 RTX 的 FEC 恢复测试同时覆盖新旧源帧。
- `regression.log`：真实内核 plain/offloaded TUN I/O 与 2000 条双栈路由增删/冲突保护/ACK 专项。
- `regression/exit-status.tsv`：九套功能场景、32 组 weaknet、自然 crossed-rekey 全通过。
  功能包括 PMTU、旧版互通、overlay 强制碰撞、多跳成员策略、Subnet Router、Exit Node、IPv6 discovery、
  DHCP policy 和 offload。旧版互通确认大 PMTU 不代表格式能力，新端 compact=false，旧端确定性恢复 8 个源包。
  另补测原始 1232 上限构建（`compatibility-1232.json`）与能力版本 1 试跑构建
  （`compatibility-v1.json`），都回退原格式、完成双向双栈传输和确定性 8 包 FEC 恢复。
  这些是互通测试，不混入性能统计。
- 自然换钥期间 120 s 持续 TCP+ICMP，6000/6000 回复；最低已证实 PMTU 1452。
  两个方向使用不同活动密钥世代，换钥后三组数据测试前后各方向 compact=true，无持久性能坍塌。
- `finish.log`：正式测量结束后重跑 Python/fmt/脚本语法检查；Nix release 包构建与包内测试也通过，见 `nix-build.log`。
  Nix 外部缓存曾返回 TLS 警告，随后完成本地构建；完整日志保留。
- 本轮未重跑百/千节点、完整 NAT 矩阵、开机/DHCP VM，也未验证高 PPS 纯 UDP 跨换钥无丢包。
  不把历史规模测试转换成当前二进制的验收。
