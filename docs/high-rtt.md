# 高 RTT：缓存扫描优化与未采用的扩容试验

本文记录 2026-09-24 的历史版本。后续容量与 TUN 准入改动见 [背压闭环](backpressure.md)。

2026-09-24。本轮区分“保留的局部优化”和“吞吐、等待时间与交付率存在取舍的试验”。
保留 GGB3、单层逐跳加密、FEC/RTX、发送速率和保护预算；**默认缓存仍为 2048 项**。

## 定位与诊断工具

原 `MAX_QUEUE=2048` 同时限制未发送队列和缓存源片（包括已发送、等待确认的副本）。
同机千兆整形、RTT 100 ms 的诊断中，原版应用吞吐约 164 Mbit/s，负载样本中缓存最高 2035 项，
发送队列均为 0，但测量期间 daemon dropped 增加 9543。待确认容量不足是一个实际限制。
RTT 20 ms 则约 592–599 Mbit/s，链路 RTT 约 22 ms、应用满载 RTT 中位数约 48 ms。
单凭链路队列快照不足以判断全部额外延迟的位置；TUN 前后的积压仍需进一步定位和治理。

`tests/perf/compare{,_loss}.py --sample-ms 200` 可保存负载期间的节点状态、TCP/UDP socket 和
TUN/WAN/router qdisc 信息。实际周期包括查询耗时，报告记录相对时间；正式吞吐对照默认关闭采样。
采样失败使试验失败，不静默丢失证据；报告保留 daemon 日志。诊断采样会扰动数据面，不与正式配对混算。

## 保留的生产改动

**跳过尚不可能到期的缓存全表扫描**：源片按序号/创建时间有序；若最老副本年龄还小于
`min(RTO, lifetime)`，任何源片都没有到重传/过期时间，直接跳过缓存遍历。
`last_sent >= created`，所以用创建时间作为快速判断是保守的；旧副本存在时仍走原扫描。

- 保持原 1 ms 维护、2 ms FEC 封组和 ACK 节拍；封组在扫描快速返回之前执行。
- 不增加计时器堆，不延后 RTX/过期判断，不修改 ACK 验证、重放或重传预算。
- 2048 项队列/缓存、128 项反馈队列、250 ms 未发期限和 1 s 源片寿命全部保持。
- 状态新增 `cache_scan_runs`、`cache_scan_sources`、`max_data_queue_wait_us`、
  `max_feedback_queue_wait_us`。最大排队时间只统计实际发出的原始源片/反馈，自世代创建累计，包含预热。
  `in_flight` 沿用原含义：缓存源片数，包括已准入但未发送的源片。
- 没有改依赖、线程数量、TUN offload/队列参数、线上格式或用户配置。

## 未采用的试验及代价

### 1. 自适应待确认缓存

试验将缓存与未发队列分开：缓存按速率与 RTT 适配 2048–8192 项，未发队列维持 2048；
所有邻居和密钥世代共用 32768 项 RAII 预留池，避免按邻居预分配大窗口。

- 仅扩容的 pilot：100 ms RTT 吞吐 448.23 Mbit/s，但满载 p99 达 329 ms。
- 扩容 + 扫描快速判断的候选：100 ms RTT 吞吐 539.28 Mbit/s，但 p99 仍为 318 ms。
  负载期间链路 RTT 约 102 ms、链路队列大多为空，应用 RTT 中位数却约 206 ms。

扩容候选该轮收到 500/500 ICMP、TCP 重传 0；相应原版诊断收到 486/500 ICMP、TCP 重传 9002，存在准入丢弃。
因此原版较低的成功回复 p99 不代表总体交互体验更好：未回复请求没有计入该分位数。
扩容改善吞吐和交付，但增加成功包的等待，需要同时衡量成功包等待和未交付请求。

**不把这个吞吐数字作为默认产品的优化成果**：容量扩展后的深队列尚未治理，暂留为候选。
最终默认代码撤回缓存扩容和共享预留池；源代码与二进制在 `large-cache-source.tar.gz` / `nnlan-large-cache`。
该候选的报告文件名为 `diagnose-final-*`（试验时命名），并非最终保留版本；以报告内哈希为准。
另一个只调整扫描间隔到 1–5 ms 的中间版本完成普通测试/构建，未做性能测量，也未保留该策略。

### 2. 缩短 TUN 队列

旧版二进制上把 txqueuelen 从 500 改为 8/32，20 ms RTT 的 ping p99 降到 33.0/42.9 ms，
但 500 个请求只收到 441/486 个，TCP 重传 35781/28651，发送 TUN drops 763/584。**不采用**。

### 3. 缩小 TUN GSO 聚合

扩容候选上把 gso_max_size 从 65535 改为 8192/16384，100 ms RTT 吞吐 521.63/535.63 Mbit/s，
p99 158/213 ms；500 个请求只收到 476/492 个，TCP 重传 47589/17167。**不采用**。
降低已收到回复的 p99 但丢失更多请求，不等于整体延迟/交付改善。

## 剩余工作

缓存不足和深队列需要一起解决，而不是单独放大缓存或缩小 TUN 环。
当前 2048 项限制仍约束高带宽时延积；本轮没有宣称高 RTT 已跑满，也未实现新的拥塞控制/公平队列。
后续应测量 TUN 隐藏队列与实际处理服务率，建立反馈及时、内存有界的准入/背压，再重试容量扩展。
原始材料、失败样本、所有候选源码/二进制均在 `target/high-rtt/`。
