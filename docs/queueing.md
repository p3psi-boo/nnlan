# 满载排队：TUN 快速读取与有界按流调度

2026-09-26。在 [待确认缓存与准入背压](backpressure.md) 之后，治理本机 TUN 的跨流队头阻塞。
实现位于 `src/runtime/ingress.rs`、`runtime/data.rs` 与事件循环；不增加用户配置、依赖或工作线程。
本页的满载 RTT 指 **TCP 大流量并发时的小流探测 RTT**，不等同于大流自身的排队时间。

## 定位到的原因

旧版在读取/处理 TUN 包时立即执行路由和链路准入，受阻则暂停整个 TUN 分支。
即使扩大了待确认缓存，内核聚合包 FIFO 中的短流仍可能排在大量 TCP 数据之后。

同机、注入双向各 50 ms 延迟的临时分段诊断，用 ICMP 原始时间戳记录四个处理位置。
扣除前 50 个样本，450 组完整请求/回复：

- 发起到 A 从 TUN 读到请求：中位 **95.93 ms**，p99 **230.66 ms**。
- A 读出到 B 写入 TUN：中位 **50.44 ms**，p99 **51.21 ms**。
- B 写入请求到 B 读出回复：中位 **0.13 ms**，p99 **0.42 ms**。
- B 读出回复到 A 写入 TUN：中位 **52.15 ms**，p99 **55.56 ms**。

因此主要额外等待发生在发送侧读出之前，而不是加解密耗费了几百毫秒。
首段也包含本机 socket/内核发送路径；这些测点并没有分别量出每一个内核子队列。
诊断代码已移除，原始日志、逐包配对在 `target/queueing/stages100.json`、`stage-summary.json`。

## 实现

### 先读取，再按流准入

- TUN 分支每轮最多读取 **4096 段或 500 μs**，跨已经就绪的 GSO 聚合包，遇到 EAGAIN 停止。
  这里只分类、复制和入队，不执行路由、加密或等待某个目标的链路容量。
- **256 个随机哈希桶**；普通 IPv4/IPv6 TCP/UDP 用五元组分类。
  IPv4 分片、带 IPv6 扩展头的流量采用地址/协议的保守分组，不把片内数据误当端口。
  哈希碰撞会共享队列，因此不是严格的一流一队列保证。
- 新流/旧流列表与按字节 DRR 调度，quantum 为本机 MTU；不对 ICMP、测试端口或探测报文特殊提权。
  单桶 FIFO。某一桶准入受阻后，该轮跳过它，继续处理其他桶。
- 每轮发送尝试最多 **128 包或 100 μs**，之后返回 `select!`。
  全部受阻时等 UDP 反馈/既有定时器，而不是忙循环；有可继续的工作时安排另一次有界调度。
- 每次重试都重新检查当前 IP 来源、成员、子网/出口策略、下一跳、格式和容量。
  不在等待队列保存旧路由、密钥、nonce 或 FEC 分组引用。

### 显式资源边界

全实例共享、按需分配，不给每个邻居预留一份：

| 资源 | 上限 |
|---|---:|
| 排队 IP 数据字节总量 | 32 MiB |
| 排队 IP 包总量 | 32768 |
| 哈希桶数 | 256 |
| 从入队起的绝对寿命 | 500 ms |

这些是 **新 ingress 队列**的硬上限，与原有待确认源片缓存额度是不同资源。
32 MiB 是待发 IP 有效字节界限，不是整个进程 RSS 界限；元数据、TUN 读缓冲、FEC/RTX、
内核队列另有占用。大桶排空后释放超过 128 项的元数据容量，避免每个空桶长期保留曾经的大环。

实例满时从当前最大字节桶移除头部，再接收新包，避免所有新短流被全局尾丢弃。
不再额外限制单桶的字节额度：高 BDP 大流可以使用空闲的共享空间，而不是总量尚有空闲就被丢弃。
重试不续期 500 ms；上限不是预填目标，也不是保证缓存任意 UDP 洪泛。
这是新增的**准入前**等待期限；原有源片**准入后**的 250 ms 未发期限和 1 s 缓存寿命保持不变。
两段是独立期限，不应把 500 ms 当作完整数据路径的总等待上限。
未缩短内核 TUN 环、关闭 GSO 或扩展线上发送窗口来制造低延迟数字。

### 为什么最终没有保留 CoDel 式早期丢弃

调度借鉴 [FQ-CoDel，RFC 8290](https://www.rfc-editor.org/rfc/rfc8290.html) 的新/旧流与字节 DRR，
但最终实现 **不是 FQ-CoDel**，没有保留试验中的 CoDel/ECN 标记状态机。
[CoDel，RFC 8289](https://www.rfc-editor.org/rfc/rfc8289.html) 的 sojourn 信号候选也做了实际对照：
在这里的内层 BBR、高 RTT 链路上，早期丢弃增加 TCP 重传并损害吞吐，短流延迟却没有继续下降。

在 200 ms 试验中，带 AQM 的候选为 425.55 Mbit/s、p99 214 ms、TCP RTX 134；
仅禁用早期 AQM 后是 462.37 Mbit/s、p99 214 ms、TCP RTX 0，均为 750/750 探测回复。
最终删除该状态机、IPv4 校验和重写和 ECN 标记代码，而不是增加一个复杂的用户调优开关。
这组单轮诊断用于决定实现方向，不替代最终构建的重复测量。

最终只在硬容量/绝对期限触发时丢弃排队包；正常准入继续尊重原有链路 pacer/缓存额度。
**短流不再跟随大流 FIFO 等待，不等于大流本身没有排队。**
大流在高 BDP 下仍可驻留数百毫秒；同一五元组内的应用请求也无法通过此调度器彼此区分。
不遵守拥塞反馈的 UDP 仍可能触及硬上限或过期，哈希碰撞也会共享等待。

### 保持不变

单层逐跳加密、GGB3 及旧节点协商、FEC/有限 RTX、保护预算、ACK 节拍、源片缓存额度、
链路软工作量水位/硬队列、PMTU、TUN MTU/GSO 参数均不变。
中继和覆盖控制消息仍走原路径；本轮不是所有中继/内核队列的端到端流控。

## 状态字段

保留 `status.tun_backpressure` 入口，包含：

- `queued_bytes` / `queued_packets`：当前 ingress 占用。
- `active_flows`：调度列表内桶数，哈希碰撞共享且空桶延后清理，不是精确五元组数量。
- `overflow_dropped` / `expired_packets`：累计超限/过期丢弃。
- `max_wait_us`：尝试出队时观察到的最大驻留时间，包含之后暂缓的包。
- `pauses`：因链路准入受阻而放回桶的次数；不再是旧版暂停整个 TUN 分支的状态切换次数。

旧版和新版 `pauses` / `max_wait_us` 的统计口径不同，不直接相减解释优化幅度。
所有实际 ingress 丢弃同步记入顶层 `dropped`。

## 候选筛选与证据

所有失败/中间候选保留在 `target/queueing/`，没有用它们替代最终配对验收：

- v1：只读取一个聚合包就进入昂贵发送处理。100 ms RTT，517.23 Mbit/s，p99 325 ms；未解决主要 FIFO 等待。
- v2：跨聚合快速读取，但单桶 2 MiB/总量 4 MiB 太小。485.86 Mbit/s、p99 134 ms，
  10 s 测量 TCP 重传 35020，整个运行队列溢出 45421；这不是可接受的低延迟修复。
- v3：16/32 MiB 硬界限清除该轮溢出，100 μs 读取预算下 p99 157 ms；吞吐 482.47 Mbit/s。
- v4：500 μs 有界快速读取，试跑 p99 114 ms、492.47 Mbit/s，500/500 ICMP，队列溢出和过期为零。
  正式结果按后面的配对数据报告，而不是把这一次试跑当稳定性能保证。

- v4 的正式 200 ms 样本暴露单桶 16 MiB 硬限额：总空间尚未用满却触发 11476 次测量期溢出。
- v5 删除单桶限额后，200 ms 不再溢出，但 250 ms 准入前寿命仍过早丢弃高 BDP 突发；
  试跑吞吐 435.66 Mbit/s、p99 216 ms、TCP RTX 7742，整轮过期 11219。
- v6 保留总量/包数硬上限，把准入前绝对寿命设为 500 ms。200 ms 试跑无溢出/过期，
  TCP RTX 降为 133，p99 213 ms；吞吐仍为 431.11 Mbit/s，而不是假称队列无溢出就解决了一切。
  该轮最大大流驻留约 319 ms：短流隔离有效，但大流本身并未达到 5 ms 排队目标。

最终纯流队列源文件约 210 行，不引入独立 AQM 配置或新的报文处理语义。

- 旧版：`18dec2ed397503df0e8071c4d46dfe6b5e72e93ba33017650ad3dad72cfae137`。
- 最终纯流队列版：`5dbd059166d3d61dc5396e9cfbe589f6340282e8a4d82a1ebfa0addb9491b722`。
- `target/queueing/nnlan-before` / `nnlan-after` 是冻结的比较二进制；不把中间候选混入最终数据。
- 同机 Xeon Gold 5218、Linux 6.18.46；owned netns/veth，底层千兆整形、TUN MTU 1280，
  内层 TCP BBR，默认逐跳认证加密及 FEC+RTX，未提高带宽配置来换结果。
- 每轮先预热 20 s，再测量 15 s，ICMP 50/s，共 750 次；可选状态采样间隔 200 ms。
  预热和测量是不同的 TCP 连接，结果包含测量连接自身的启动过程，不是排除启动后的纯稳态值。
- 100/200 ms 各三组新旧配对，顺序轮换；20 ms、双向各 1% 丢包及直连各一组。
  高 RTT/丢包场景采用三 namespace 路由夹具，在故障边界禁用 veth 聚合并检查实际包长；
  直连使用原两 namespace 夹具，不把不同夹具的结果混成同一个基线。
- 编译、其他网络测试与性能测量不并行。原始数据保留各轮 CPU、队列、重传、ping 文本和精确参数。
  这是同机夹具结果，不代表真实 NIC/WAN 或多跳、Subnet Router/Exit Node 的性能保证。

## 最终配对结果

100/200 ms 两行分别取三轮 goodput 与各轮 p99 的中位数；其他行各一轮。
所有速率是接收端应用 goodput，不是加上 FEC/RTX 的线上记账速率。

| 条件 | 旧→新 Mbit/s | 满载 p99 旧→新 ms | 新版 ICMP 收到/发出 |
|---|---:|---:|---:|
| 直连 IPv4 | 763.47→762.81 | 3.81→3.27 | 750/750 |
| 直连 IPv6 | 750.77→751.02 | 5.96→3.11 | 750/750 |
| 直连 IPv4 反向 | 763.18→763.43 | 6.36→3.08 | 750/750 |
| RTT 20 ms | 601.80→574.47 | 65.6→33.8 | 750/750 |
| RTT 100 ms，三轮 | **542.98→506.24** | **304→114** | **2250/2250** |
| RTT 200 ms，三轮 | **494.05→461.09** | **520→215** | **2250/2250** |
| RTT 100 ms、双向各 1% 丢包 | 447.12→428.69 | 296→119 | 750/750 |

- 100/200 ms 的高 RTT 吞吐中位数分别下降 **6.77% / 6.67%**。这是本轮明确的代价，
  不是“吞吐和延迟全部提升”；直连仍约 763 Mbit/s，单轮的小差异不作显著性结论。
- 两组高 RTT 的六次新版测量没有漏掉探测回复；不是丢弃大量探测包后只统计成功回复。
  旧版也都收到全部回复，比较口径一致。
- 100 ms 三轮 TCP RTX 均为 0；200 ms 新版三轮为 **3、4、0**，旧版均为 0。
  20 ms 与直连均为 0；1% 故障样本旧→新 **38→42**。
- 最终性能矩阵的全部新版测量区间，双端内核 TUN TX 丢包、ingress 超限丢弃与过期均为 **0**。
  这不包括刻意过载的功能测试：在那里期限丢弃应当发生。
- 采样观察到的最大 ingress 占用为 **24,625,972 字节**（约 23.49 MiB），不是精确峰值或 RSS。
  大流仍可产生数百毫秒的驻留，因此不能把短流 p99 改善解读为所有包的队列都已清空。

逐轮值、状态差分与队列采样摘要在 `target/queueing/paired-summary.json`；
最终样本没有覆盖百/千进程持续业务、真实 NIC、任意流数/哈希碰撞、真实 WAN 的稳态长期性能。
后续吞吐工作应在这个保留短流隔离的版本上继续测量，而不是恢复一个全局 FIFO 来提高单流数字。

## 回归与交付边界

最终构建实际通过：

- `cargo fmt --check`、严格 clippy、**195 项 Rust**（177 库内 + 18 集成）、release 构建。
  另有 2 项显式 ignored 的内核专项未在本轮单独运行。
- **16 项 Python**：规模工具 9、性能工具 7。
- **8 套真实网络回归**：
  1. 2 Mbit/s 限速过载：UDP/管理进展、双栈 TUN 到另一目标的全部探测回复、队列界限、
     负载期间撤销成员、另一链路继续通信。采样管理 RPC 最长约 18.2 ms；
     故意过载时累计 23319 个 ingress 包按期限丢弃，结束后队列为空。
  2. GSO/GRO：IPv4/IPv6、双向、原始 128×100 / 48×1200 / 64×900 字节突发，
     完整交付且不依赖应用重试。
  3. PMTU 收缩/增长、ICMP 被过滤的路径、双栈和完整 TUN MTU。
  4. 多跳 trace 与真实 IPv4 碰撞恢复。
  5. 成员撤销及持续本地拒绝。
  6. 与旧 GGB3 非紧凑格式版本互通及 FEC 恢复。
  7. 默认 FEC+RTX 的 8 种弱网场景（不是全部 32 种修复策略组合）。
  8. 自然交叉换钥：连续 **6000/6000 ICMP**，换钥后三组 IPv4/IPv6/反向 TCP 继续工作。

22 次最终性能运行与 8 套网络报告已逐一检查成功状态和可用的二进制哈希，测试 namespace 已清理。
验证摘要 `target/queueing/validation.json`，完整日志 `regression/`，源码归档/差异及校验清单均在同目录。
